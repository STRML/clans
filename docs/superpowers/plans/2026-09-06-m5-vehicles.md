# Milestone 5: Vehicles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Shrike and the Wildcat exist, fly and drive, and can be spawned, mounted, fought in, and destroyed. A player standing at a powered vehicle pad's use radius opens a station-like menu, picks Shrike or Wildcat, and the pad spawns it (destroying any vehicle it already hosts) so long as the team is not already at its pad-derived cap. Walking up to an unoccupied vehicle and pressing `E` mounts it: the pilot's own weapons go silent, the camera moves to the vehicle, and the vehicle answers to WASD/mouse with the real T2 forces for its type. The Shrike flies — thrust, lift, mouse pitch/yaw, auto-roll, auto-stabilize below `maxAutoSpeed`, afterburner from energy — and collides with terrain and interiors like everything else in `sim`. The Wildcat hovers on a real spring (`stabLenMin`/`stabLenMax`, `stabSpringConstant`, `stabDampingConstant`) with forward/reverse/strafe thrust, a boost, a jump, and lean-into-the-turn steering. Both vehicles take collision, ground-impact, and weapon damage against a shielded energy pool exactly like a base turret's shield rule, and explode past `maxDamage`, flinging the pilot clear with the real ejection numbers and 0.4 crash damage. The Shrike's twin-barrel blaster (0.125 direct, 425 m/s) fires from the driver's own fire input. Each team's AA barrel — placed and powered by milestone 4 but left permanently idle because no vehicle existed to target — now finds, tracks, and fires on enemy vehicles in range with line of sight, closing the one deliberate gap M4's own Spec gaps section named. Vehicle state rides in the snapshot like every other extra, predicted locally for the driver and interpolated for everyone else. The HUD shows vehicle health and speed while mounted. A Playwright test spawns a Wildcat, mounts it, drives it, and dismounts.
**Architecture:** `packages/sim` gains `vehicles.ts` (`VehicleStore`, `VEHICLE_DATA`, `spawnVehicleAtPad`, `stepVehicles` — physics for both kinds, mount/dismount, the Shrike blaster's fire-event production, ejection, and vehicle shield damage) and grows `movement.ts` (a mounted player skips their own movement pipeline entirely), `weapons.ts` (a mounted player's own weapon system is inert), `projectiles.ts` (vehicles join players/base objects/turrets as a hittable/blocking category; a new `spawnVehicleShot` drains `pendingVehicleFireEvents` the same tick `stepVehicles` produces them, mirroring M4's `spawnTurretShot`), `turrets.ts` (the AA barrel's target-acquisition scan, dormant since M4, now also considers `world.vehicles`), `hash.ts`, and `snapshot.ts`. `stepWorld` grows one more fixed-order call. `packages/protocol` adds `MessageType.VehicleSpawn`, a `use` input bit, and `VehicleSnapshotData` to `WorldExtras`. `packages/assets` fetches and converts the two vehicle `.glb` files the spec names by name (`vehicle_air_scout.glb`, `vehicle_grav_scout.glb`), both confirmed present on `exogen/t2-mapper` in this planning session, with an STL-then-procedural fallback chain built generically enough for a future asset to reuse. `packages/server` loads vehicle data, wires `VehicleSpawn`, and broadcasts vehicle extras. `packages/client` renders vehicles, adds a vehicle-pad menu, moves the camera onto the vehicle while mounted, and extends the HUD.
**Tech Stack:** the milestone 4 stack unchanged — no new dependency in any package.
**Spec:** docs/superpowers/specs/2026-09-05-clans-tribes2-browser-demo-design.md
**Baseline:** `main` at `e19f93f` ("M4: base assets and power (#11)", merged). M4 is real, merged code now, not a plan document — this plan was originally drafted against the M4 *plan's* stated interfaces while M4 was still an unmerged branch, and has since been reconciled against the actual merge, including the fixes from a 3-round Codex review on PR #11. Every M4 interface this plan depends on was re-verified directly against `packages/sim/src/baseObjects.ts`, `turrets.ts`, `armor.ts`, `interiors.ts`, and `packages/protocol/src/{messages,snapshot,handshake}.ts` on `main`:

- `BaseObjectKind` (`Generator = 0, Sensor = 1, StationInventory = 2, StationVehiclePad = 3, ForceField = 4`), `teamHasPower(world, team)`, `stationAt(world, playerId)` all match this plan's assumptions exactly. `stationAt` does exclude a destroyed station (Codex round 1, finding 5 on PR #11) — this plan never called `stationAt` itself, so that fix does not change anything here, but it does confirm the pattern this plan's own `spawnVehicleAtPad`/`poweredPadsForTeam` should follow. **`BaseObjectStore` has no `active` field** — a base object is never removed once placed, so existence is `id < store.count`, not a boolean flag (see `teamHasPower`'s own doc comment on `main`). This plan's Task 1 originally read `!baseObjects.active[padId]`/`!baseObjects.active[id]`; both are fixed below, since that field does not exist and the field lookup would be `undefined` (falsy), silently rejecting every pad.
- `interiors.ts` exports exactly `raycastInteriors(interiors: readonly InteriorInstance[], origin: Vec3, direction: Vec3, maxDistance: number, stats?): {distance, point, normal} | null` and `resolveSphereAgainstInteriors(interiors, center: Vec3, radius: number, stats?): Vec3 | null` — both names match this plan's assumption, but `raycastInteriors` takes a **normalized direction and a scalar distance**, not two points. M4's round-1 fix for player/force-field movement tunnelling (`movement.ts`'s `sweepChest`) established the pattern: normalize `(current - previous)` into a direction and length before calling it. Task 4 originally called `raycastInteriors(world.interiors, previousPosition, current)` — three args, second point where a direction belongs. Fixed below to mirror `sweepChest`.
- `turrets.ts` ships `hasLineOfSight(world, from, to)` (matches), `TurretBarrelId.AABarrelLarge = 1` (matches), and a real, private target-acquisition pipeline this plan's Task 8 originally hedged about not having re-read: `acquireTarget(world, id): number` (scans `world.players` only), `targetStillValid(world, id): boolean`, and `fireAt(world, id): void` (reads `world.players.position` directly to compute the fire direction and pushes a `TurretFireEvent`). Critically, **`TurretFireEvent` carries no target-id field at all** — `{ turretId, barrel, team, origin, direction }`, direction already resolved by the time it's queued — so a "player-or-vehicle" discriminator cannot live on the fire event the way this plan's Task 8 originally proposed; it has to live on `TurretStore.targetId`'s own referent instead. Fixed below.
- `activeForceFieldBlockers(world, forTeam): InteriorInstance[]` matches exactly.
- `WorldExtras.baseObjects`/`WorldExtras.turrets` exist and match this plan's assumed shape. `MessageType.Loadout = 8` is confirmed real (`packages/protocol/src/messages.ts`), so `MessageType.VehicleSpawn = 9` is still the next free value — no change needed there. **`PROTOCOL_VERSION` is still `2` on `main`** — M4 added `Loadout`, the `packActive` bit, and the `baseObjects`/`turrets` extras without bumping it, so this plan's Global Constraints hedge about "becomes 4 if M4 already moved it" does not apply: the bump to `3` in Task 10 is correct as written.
- `armorFor(world, id)` and the `ARMORS`/`ArmorId` table match exactly (used by Task 7's ejection-impulse mass lookup).
- The real client-side seeding pattern (`packages/client/src/netclient.ts` + `app.ts`) is **not** "NetClient seeds base objects/turrets/force fields." It is: `app.ts`'s `createApp` seeds `world.baseObjects`/`world.turrets` **statically once**, before a `NetClient` even exists, straight from the shared `assets.scene.baseObjects`/`assets.scene.turrets` array the server's own `loadKatabaticWorld` places objects from (same array, same order, so ids already line up) — for *both* the single-player and networked paths. `NetClient.handleSnapshot` then applies only the *dynamic* fields (`damage`/`destroyed`/`powered`/...) onto that pre-seeded store by id, every snapshot, via `applyBaseObjectSnapshot`/`applyTurretSnapshot`. Vehicles have **no mission-file placement to pre-seed from** — Katabatic's `.mis` places only the pad, never a vehicle — so this two-phase pattern cannot apply as-is. Task 9/13 are fixed below to make `deserializeVehicle` do double duty: growing `world.vehicles.count`/setting `active[id] = 1` for an id the client has never locally created, the same "grow to fit" move `applyBaseObjectSnapshot` makes for a *never-placed* base-object id, but for vehicles this is the *only* path an id is ever created client-side, not a fallback for a rare edge case.

Every task below cites the real file and, where it matters, the real function/field name directly, rather than a plan-of-a-plan reference.

## Global Constraints

- `stepWorld(world, inputs, dt = FIXED_DT)` stays the only public sim entry point and keeps its exact signature. **The real, merged `main` order (`packages/sim/src/world.ts`) is `stepPlayers`, `stepWeapons`, `stepTurrets`, `stepProjectiles`, `stepPower`, `stepRepairPacks`, `stepFlags`, `world.tick += 1` — not the order this plan originally assumed.** M4's own Codex round 1, finding 5 deliberately moved `stepPower` to *after* `stepProjectiles` (not before `stepTurrets`, where this plan's draft — following the M4 *plan* document rather than the merge — had it): a generator destroyed by this tick's own projectile damage needs to clear its team's power the same tick, not the next one, and `teamHasPower`'s destroyed-generator exclusion only helps if `stepPower` runs after the damage that could destroy one. This plan's call order is corrected to insert `stepVehicles` between `stepWeapons` and `stepTurrets`: **`stepPlayers`, `stepWeapons`, `stepVehicles`, `stepTurrets`, `stepProjectiles`, `stepPower`, `stepRepairPacks`, `stepFlags`, then `world.tick += 1`.** This still gives `stepVehicles` everything it needs same-tick: it runs before `stepTurrets` so a turret's AA barrel sees this tick's vehicle positions before it decides whether to acquire or fire, and before `stepProjectiles` so a Shrike blaster shot fired this tick is already in `world.pendingVehicleFireEvents` for `stepProjectiles` to materialize in the *same* tick — exactly the relationship `stepTurrets` → `stepProjectiles` already has for turret shots on `main`. It does *not* need to run before `stepPower`, and on `main` nothing does except `stepProjectiles` itself (per the round-1 fix above) — `spawnVehicleAtPad`'s own pad-power gate calls `teamHasPower(world, team)` directly rather than reading the previous tick's `baseObjects.powered[padId]` bit, specifically so it is never stale regardless of where `stepPower` sits in the tick. `stepPlayers` runs first, unchanged in position, but a mounted player's own entry in it becomes a no-op (see Task 5) rather than being skipped outright, so every other per-player bookkeeping `stepPlayers` does (weapon timers advancing to a frozen state, `wasJumpHeld` clearing) still happens for a mounted id. `stepFlags` stays last. No package outside `sim` calls a step function directly.
- `packages/sim` still imports nothing from DOM, Three.js, WebSocket, or Node. There is no vehicle placement data to load at world-build time — unlike base objects and turrets, vehicles do not exist in the mission file at all (Katabatic's `.mis` places the *pad*, an M4 `BaseObjectKind.StationVehiclePad`, not a vehicle); every vehicle is created at runtime by `spawnVehicleAtPad`, which only ever needs a `padId` already present in `world.baseObjects`.
- Every ESLint `complexity: 10` / `max-depth: 3` budget holds. `vehicles.ts`'s two physics steppers (`stepShrike`, `stepWildcat`) are split into named helpers the way `movement.ts`'s `classify`/`applyForces`/`integrate`/`writeState` already are — force accumulation, orientation integration, and ground/hover contact each get their own function, not one long `stepVehicles` body with a kind switch inside it.
- **A mounted player's position is not simulated by `movement.ts` at all.** `stepPlayer` (`movement.ts`) gains one guard at its top: `if (world.players.mountedVehicleId[id] !== -1) return;` — no gravity, no run/jet/jump, no interior/force-field collision pass runs for a mounted id. `stepVehicles` is the only system that writes a mounted player's `position`/`velocity` (seat-locked to the vehicle, an offset from the vehicle's own transform), after it moves the vehicle itself. This mirrors the real T2 rule (a mounted player's `Player::updateMove` never runs; the vehicle's transform carries the passenger) and keeps ownership of "who moves this id this tick" unambiguous — exactly one system writes a given player's transform on a given tick, mounted or not.
- **A mounted player's own weapon system is inert.** `weapons.ts`'s `stepOnePlayer` gains the same guard as `movement.ts`'s: a mounted player's weapon-state-machine timer does not advance and their `fire`/`altFire`/`slot` input is ignored by `tryFireWeapon`/`applySlot`. The vehicle's own weapon (the Shrike blaster; the Wildcat has none, matching the spec's own Vehicle numbers table and the real `vehicle_wildcat.cs`, which defines no weapon datablock at all) reads the driver's `fire` input directly inside `stepVehicles` instead — see Task 6.
- **`use` is a new wire-level `PlayerInput` bit, not a client-local decision, and this is a deliberate reversal of an M4 assumption.** M4's Task 7 states plainly that station use "has no wire representation at all" because opening a station menu is a fact both sides already compute identically from state they already have, and only the final loadout choice needs to reach the server. Mounting a vehicle is not that: which player controls which vehicle is authoritative state the server alone decides (two players racing for the same Wildcat must not both believe they got it), so the server has to see the use key. `PlayerInput` gains `use: boolean` (protocol bit 5, value 32 — see Task 10), read every tick like `jump`/`jet`, edge-detected inside `vehicles.ts` itself (a private `wasUseHeld: Uint8Array` on `PlayerStore`, not shared with `movement.ts`'s own `wasJumpHeld`, since only `stepVehicles` needs it and coupling it into `movement.ts` would mean one more file Task 5 has to touch for no benefit). A held `E` near a station still only opens a local menu, per M4; a held `E` near an unoccupied vehicle (or the vehicle you are already in) additionally sends `use: true` on the wire, and `stepVehicles` treats its *rising edge* as the mount/dismount trigger — see Task 5.
- Numbers with a spec citation are used exactly as the spec's Vehicle numbers table states them. Numbers the spec does not give are pulled from the cited T2 base script at `jdknight/t2ds` (script and line range cited inline, all fetched and read in this session — `GameData/base/scripts/vehicles/vehicle_shrike.cs`, `vehicles/vehicle_wildcat.cs`, `vehicles/vehicle.cs`, `weapons/chaingun.cs`, `turrets/aaBarrelLarge.cs`) or, failing that, picked here, marked **ours**, and collected in the numbers table below.
- Vehicles are shielded exactly like an M4 base object or turret: `applyVehicleDamage` spends `min(energy / energyPerDamagePoint, amount)` worth of a hit against `energy` first (`energy -= spent * energyPerDamagePoint`), the remainder against `damage`, using the same mechanic M4's Global Constraints established for `applyBaseObjectDamage`/turret damage and the spec's own "shields (Shield Pack, vehicles, base turrets) spend energy at `energyPerDamagePoint` before health" line — this is the first sim code to apply that rule to a *vehicle* specifically, though the mechanic itself is M4's, not new here.
- Turret line of sight for AA targeting reuses M4's `hasLineOfSight(world, from, to)` (`turrets.ts`, Task 4) unchanged — a vehicle's eye point for this check is its own position (no separate "turret eye height" fudge is needed the way M4 needed one for a static turret base, because a vehicle's position already sits at flight/hover altitude).
- `packages/bots` stays the milestone-2 placeholder; no bot brains ship this milestone (milestone 6). The 31 idle bots never press `use`, never spawn or pilot a vehicle, and are never targeted preferentially by the AA barrel over a real client's vehicle — same "no notion of bot vs. human" rule M4 stated for ground turrets, now extended to the AA barrel's own targeting.
- `PROTOCOL_VERSION` bumps from 2 to 3 (Task 10): this milestone changes the wire format in three ways a client from an earlier version cannot silently ignore (a new `MessageType`, a new input flag bit, a new `WorldExtras` field), and `WelcomeStatus.VersionMismatch` already exists specifically to reject a stale client rather than let it desync. **Confirmed against `main`:** `PROTOCOL_VERSION` is still `2` (`packages/protocol/src/messages.ts`) — M4 added `Loadout`, `packActive`, and the `baseObjects`/`turrets` extras without bumping it, so this milestone's bump to `3` is correct as written and needs no adjustment.

function allocate(store: VehicleStore): number | null {
  const id = store.freeIds.pop() ?? store.count;
  if (id >= store.active.length) return null;
  if (id === store.count) store.count += 1;
  return id;
}

function poweredPadsForTeam(baseObjects: BaseObjectStore, world: World, team: number): number[] {
  const ids: number[] = [];
  // BaseObjectStore has no `active` field on main -- a base object is never removed once
  // placed, so "exists" is exactly `id < baseObjects.count` (see baseObjects.ts's own
  // teamHasPower doc comment), which this loop's bound already guarantees. An earlier draft
  // of this plan read `!baseObjects.active[id]` here, which is `undefined` (always falsy) on
  // the real store and would have silently rejected every pad on every call.
  for (let id = 0; id < baseObjects.count; id += 1) {
    if (baseObjects.kind[id] !== BaseObjectKind.StationVehiclePad) continue;
    if (baseObjects.team[id] !== team) continue;
    if (!teamHasPower(world, team)) continue;
    ids.push(id);
  }
  return ids;
}

export function vehicleCapForTeam(world: World, team: number): number {
  return poweredPadsForTeam(world.baseObjects, world, team).length;
}

export function activeVehicleCountForTeam(world: World, team: number): number {
  const vehicles = world.vehicles;
  let count = 0;
  for (let id = 0; id < vehicles.count; id += 1) {
    if (vehicles.active[id] && !vehicles.destroyed[id] && vehicles.team[id] === team) count += 1;
  }
  return count;
}

function destroyExistingAtPad(world: World, padId: number): void {
  const vehicles = world.vehicles;
  for (let id = 0; id < vehicles.count; id += 1) {
    if (vehicles.active[id] && !vehicles.destroyed[id] && vehicles.padId[id] === padId) {
      // Task 7 owns the real destruction/ejection path; Task 1 only needs the flag set so
      // the new spawn below is never blocked by "old vehicle still counts against the cap."
      vehicles.destroyed[id] = 1;
    }
  }
}

export function spawnVehicleAtPad(world: World, padId: number, kind: VehicleKind): number | null {
  const baseObjects = world.baseObjects;
  // Existence check only -- `id < count` is the real store's whole existence contract (no
  // `active` field; see poweredPadsForTeam's own comment above). A destroyed check would be
  // a no-op in practice: BaseObjectKind.StationVehiclePad is `invincible: true` in
  // baseObjects.ts (station.cs:235-247 -- `isInvincible = true`, no `maxDamage` field at
  // all), so `applyBaseObjectDamage` never sets `destroyed` on a pad in the first place.
  if (padId < 0 || padId >= baseObjects.count) return null;
  if (baseObjects.kind[padId] !== BaseObjectKind.StationVehiclePad) return null;
  const team = baseObjects.team[padId] ?? 0;
  if (!teamHasPower(world, team)) return null;
  if (activeVehicleCountForTeam(world, team) >= vehicleCapForTeam(world, team)) return null;

  destroyExistingAtPad(world, padId);

  const id = allocate(world.vehicles);
  if (id === null) return null;
  const vehicles = world.vehicles;
  const base = padId * 3;
  const padPos: Vec3 = {
    x: baseObjects.position[base] ?? 0,
    y: baseObjects.position[base + 1] ?? 0,
    z: baseObjects.position[base + 2] ?? 0,
  };
  vehicles.active[id] = 1;
  vehicles.kind[id] = kind;

import { GRAVITY } from './movement.js';
import type { PlayerInput } from './types.js';

const SHRIKE_MIN_DRAG = 30;
const SHRIKE_MANEUVERING_FORCE = 3000; // vehicles/vehicle_shrike.cs:140
const SHRIKE_STEERING_FORCE = 1200; // vehicles/vehicle_shrike.cs:141
const SHRIKE_ROLL_FORCE = 4; // vehicles/vehicle_shrike.cs:143
const SHRIKE_HORIZONTAL_SURFACE_FORCE = 6; // vehicles/vehicle_shrike.cs:138
const SHRIKE_VERT_THRUST_MULTIPLE = 3; // vehicles/vehicle_shrike.cs:152
const SHRIKE_MAX_AUTO_SPEED = 15; // vehicles/vehicle_shrike.cs:131
const SHRIKE_AUTO_ANGULAR_FORCE = 400; // vehicles/vehicle_shrike.cs:131 — ours table
const SHRIKE_AUTO_LINEAR_FORCE = 300; // vehicles/vehicle_shrike.cs:132 — ours table
const SHRIKE_ROTATIONAL_DRAG = 900; // vehicles/vehicle_shrike.cs:128 — ours table
const SHRIKE_JET_FORCE = 2000;
const SHRIKE_MIN_JET_ENERGY = 28;
const SHRIKE_JET_ENERGY_DRAIN = 2.8;

function headingOf(yaw: number, pitch: number): Vec3 {
  const cp = Math.cos(pitch);
  return { x: Math.sin(yaw) * cp, y: Math.sin(pitch), z: Math.cos(yaw) * cp };
}

/** Auto-stabilizer: below maxAutoSpeed, angular velocity relaxes toward zero and linear
 *  velocity toward zero, at autoAngularForce/autoLinearForce -- Torque's own "when you let
 *  go of the stick it levels out" behavior. */
function applyAutoStabilize(vehicles: VehicleStore, id: number, speed: number, dt: number): void {
  if (speed >= SHRIKE_MAX_AUTO_SPEED) return;
  const angBase = id * 3;
  for (let axis = 0; axis < 3; axis += 1) {
    const av = vehicles.angVel[angBase + axis] ?? 0;
    vehicles.angVel[angBase + axis] =
      av - Math.sign(av) * Math.min(Math.abs(av), (SHRIKE_AUTO_ANGULAR_FORCE / 1000) * dt);
  }
  const velBase = id * 3;
  for (let axis = 0; axis < 3; axis += 1) {
    const v = vehicles.velocity[velBase + axis] ?? 0;
    vehicles.velocity[velBase + axis] =
      v - Math.sign(v) * Math.min(Math.abs(v), (SHRIKE_AUTO_LINEAR_FORCE / VEHICLE_DATA[VehicleKind.Shrike].mass) * dt);
  }
}

function applyShrikeSteering(vehicles: VehicleStore, id: number, input: PlayerInput, dt: number): void {
  const angBase = id * 3;
  // Mouse yaw/pitch accelerate angular velocity via steeringForce, not snap the angle --
  // integrated below like everything else, so a held mouse input ramps, matching the real
  // steering-jet model rather than a direct-set rotation.
  vehicles.angVel[angBase + 1] = (vehicles.angVel[angBase + 1] ?? 0) + input.yaw * (SHRIKE_STEERING_FORCE / VEHICLE_DATA[VehicleKind.Shrike].mass) * dt;
  vehicles.angVel[angBase] = (vehicles.angVel[angBase] ?? 0) + input.pitch * (SHRIKE_STEERING_FORCE / VEHICLE_DATA[VehicleKind.Shrike].mass) * dt;
  vehicles.angVel[angBase + 2] = (vehicles.angVel[angBase + 2] ?? 0) - SHRIKE_ROLL_FORCE * dt * Math.sign(vehicles.roll[id] ?? 0);
  vehicles.yaw[id] = (vehicles.yaw[id] ?? 0) + (vehicles.angVel[angBase + 1] ?? 0) * dt;
  vehicles.pitch[id] = (vehicles.pitch[id] ?? 0) + (vehicles.angVel[angBase] ?? 0) * dt;
  vehicles.roll[id] = (vehicles.roll[id] ?? 0) + (vehicles.angVel[angBase + 2] ?? 0) * dt;
  vehicles.angVel[angBase] = (vehicles.angVel[angBase] ?? 0) * (1 - Math.min(1, (SHRIKE_ROTATIONAL_DRAG / 1000) * dt));
  vehicles.angVel[angBase + 1] = (vehicles.angVel[angBase + 1] ?? 0) * (1 - Math.min(1, (SHRIKE_ROTATIONAL_DRAG / 1000) * dt));
}

export function stepShrike(world: World, id: number, input: PlayerInput, dt: number): void {
  const vehicles = world.vehicles;
  const data = VEHICLE_DATA[VehicleKind.Shrike];
  const base = id * 3;
  const heading = headingOf(vehicles.yaw[id] ?? 0, vehicles.pitch[id] ?? 0);

  applyShrikeSteering(vehicles, id, input, dt);

  // Thrust along heading (W/S), lateral maneuvering (A/D) -- both driven by moveZ/moveX
  // exactly like a player's own move axes, reused rather than reinvented.
  const thrust = SHRIKE_MANEUVERING_FORCE / data.mass;
  vehicles.velocity[base] = (vehicles.velocity[base] ?? 0) + heading.x * input.moveZ * thrust * dt;
  vehicles.velocity[base + 1] = (vehicles.velocity[base + 1] ?? 0) + heading.y * input.moveZ * thrust * dt * SHRIKE_VERT_THRUST_MULTIPLE;
  vehicles.velocity[base + 2] = (vehicles.velocity[base + 2] ?? 0) + heading.z * input.moveZ * thrust * dt;

  // Afterburner.
  if (input.jet && (vehicles.energy[id] ?? 0) >= SHRIKE_MIN_JET_ENERGY) {
    vehicles.velocity[base] = (vehicles.velocity[base] ?? 0) + heading.x * (SHRIKE_JET_FORCE / data.mass) * dt;
    vehicles.velocity[base + 1] = (vehicles.velocity[base + 1] ?? 0) + heading.y * (SHRIKE_JET_FORCE / data.mass) * dt;
    vehicles.velocity[base + 2] = (vehicles.velocity[base + 2] ?? 0) + heading.z * (SHRIKE_JET_FORCE / data.mass) * dt;
    vehicles.energy[id] = (vehicles.energy[id] ?? 0) - SHRIKE_JET_ENERGY_DRAIN;
  } else {
    vehicles.energy[id] = Math.min(data.maxEnergy, (vehicles.energy[id] ?? 0) + data.rechargeRate);
  }

  // Lift: horizontalSurfaceForce provides "bite" that opposes gravity while moving forward.
  const forwardSpeed = vehicles.velocity[base] * heading.x + vehicles.velocity[base + 2] * heading.z;
  vehicles.velocity[base + 1] =
    (vehicles.velocity[base + 1] ?? 0) + Math.max(0, forwardSpeed) * (SHRIKE_HORIZONTAL_SURFACE_FORCE / data.mass) * dt;

  // Gravity and minDrag.
  vehicles.velocity[base + 1] = (vehicles.velocity[base + 1] ?? 0) - GRAVITY * dt;
  const dragScale = 1 - Math.min(1, (SHRIKE_MIN_DRAG / data.mass) * dt);
  vehicles.velocity[base] = (vehicles.velocity[base] ?? 0) * dragScale;
  vehicles.velocity[base + 2] = (vehicles.velocity[base + 2] ?? 0) * dragScale;

  const speed = Math.hypot(vehicles.velocity[base] ?? 0, vehicles.velocity[base + 1] ?? 0, vehicles.velocity[base + 2] ?? 0);
  applyAutoStabilize(vehicles, id, speed, dt);

  vehicles.position[base] = (vehicles.position[base] ?? 0) + (vehicles.velocity[base] ?? 0) * dt;
  vehicles.position[base + 1] = (vehicles.position[base + 1] ?? 0) + (vehicles.velocity[base + 1] ?? 0) * dt;
  vehicles.position[base + 2] = (vehicles.position[base + 2] ?? 0) + (vehicles.velocity[base + 2] ?? 0) * dt;
}

const WILDCAT_STAB_LEN_MAX = 3.75; // vehicles/vehicle_wildcat.cs:147

const WILDCAT_REVERSE_THRUST = 10; // vehicles/vehicle_wildcat.cs:139

const WILDCAT_TURBO_FACTOR = 1.5; // vehicles/vehicle_wildcat.cs:141
const WILDCAT_BRAKING_FORCE = 25; // vehicles/vehicle_wildcat.cs:143
const WILDCAT_BRAKING_ACTIVATION_SPEED = 4; // vehicles/vehicle_wildcat.cs:144

function applyHoverSpring(world: World, vehicles: VehicleStore, id: number, dt: number): void {
  const base = id * 3;
  const x = vehicles.position[base] ?? 0;
  const z = vehicles.position[base + 2] ?? 0;
  const ground = sampleTerrain(world.terrain, x, z).height;
  const height = (vehicles.position[base + 1] ?? 0) - ground;
  const restHeight = (WILDCAT_STAB_LEN_MIN + WILDCAT_STAB_LEN_MAX) / 2;
  const compression = restHeight - height;
  const springForce = compression * WILDCAT_STAB_SPRING;
  const dampingForce = -(vehicles.velocity[base + 1] ?? 0) * WILDCAT_STAB_DAMPING;
  vehicles.velocity[base + 1] =
    (vehicles.velocity[base + 1] ?? 0) + ((springForce + dampingForce) / VEHICLE_DATA[VehicleKind.Wildcat].mass) * dt - GRAVITY * dt;
  vehicles.onGround[id] = height <= WILDCAT_STAB_LEN_MAX ? 1 : 0;
}

function applyWildcatSteering(vehicles: VehicleStore, id: number, input: PlayerInput, dt: number): void {
  const angBase = id * 3;
  vehicles.angVel[angBase + 1] = (vehicles.angVel[angBase + 1] ?? 0) + input.yaw * (WILDCAT_STEERING_FORCE / VEHICLE_DATA[VehicleKind.Wildcat].mass) * dt;
  vehicles.yaw[id] = (vehicles.yaw[id] ?? 0) + (vehicles.angVel[angBase + 1] ?? 0) * dt;
  // Lean into the turn: roll follows yaw rate, restoring toward level via gyroDrag.
  vehicles.roll[id] = (vehicles.roll[id] ?? 0) + (vehicles.angVel[angBase + 1] ?? 0) * dt * (WILDCAT_ROLL_FORCE / 100);
  vehicles.roll[id] = (vehicles.roll[id] ?? 0) * (1 - Math.min(1, (WILDCAT_GYRO_DRAG / 100) * dt));
  vehicles.angVel[angBase + 1] = (vehicles.angVel[angBase + 1] ?? 0) * (1 - Math.min(1, (WILDCAT_GYRO_DRAG / 100) * dt));
}

function applyWildcatThrust(vehicles: VehicleStore, id: number, input: PlayerInput, dt: number): void {
  const base = id * 3;
  const heading = headingOf(vehicles.yaw[id] ?? 0, 0);
  const right: Vec3 = { x: heading.z, y: 0, z: -heading.x };
  const boosting = input.jet && (vehicles.energy[id] ?? 0) >= WILDCAT_MIN_JET_ENERGY;
  const forwardForce = (input.moveZ >= 0 ? WILDCAT_MAIN_THRUST : WILDCAT_REVERSE_THRUST) * (boosting ? WILDCAT_TURBO_FACTOR : 1);
  const mass = VEHICLE_DATA[VehicleKind.Wildcat].mass;
  vehicles.velocity[base] = (vehicles.velocity[base] ?? 0) + heading.x * input.moveZ * (forwardForce / mass) * dt;
  vehicles.velocity[base + 2] = (vehicles.velocity[base + 2] ?? 0) + heading.z * input.moveZ * (forwardForce / mass) * dt;
  vehicles.velocity[base] = (vehicles.velocity[base] ?? 0) + right.x * input.moveX * (WILDCAT_STRAFE_THRUST / mass) * dt;
  vehicles.velocity[base + 2] = (vehicles.velocity[base + 2] ?? 0) + right.z * input.moveX * (WILDCAT_STRAFE_THRUST / mass) * dt;
  if (boosting) vehicles.energy[id] = (vehicles.energy[id] ?? 0) - WILDCAT_JET_ENERGY_DRAIN;
  else vehicles.energy[id] = Math.min(VEHICLE_DATA[VehicleKind.Wildcat].maxEnergy, (vehicles.energy[id] ?? 0) + VEHICLE_DATA[VehicleKind.Wildcat].rechargeRate);

  const horizSpeed = Math.hypot(vehicles.velocity[base] ?? 0, vehicles.velocity[base + 2] ?? 0);
  if (input.moveX === 0 && input.moveZ === 0 && horizSpeed > WILDCAT_BRAKING_ACTIVATION_SPEED) {
    const scale = Math.max(0, 1 - (WILDCAT_BRAKING_FORCE / mass) * dt);
    vehicles.velocity[base] = (vehicles.velocity[base] ?? 0) * scale;
    vehicles.velocity[base + 2] = (vehicles.velocity[base + 2] ?? 0) * scale;
  }
}

function applyWildcatJump(vehicles: VehicleStore, id: number, input: PlayerInput): void {
  if (!input.jump || !vehicles.onGround[id]) return;
  if ((vehicles.energy[id] ?? 0) < WILDCAT_MIN_JET_ENERGY) return;
  const mass = VEHICLE_DATA[VehicleKind.Wildcat].mass;
  vehicles.velocity[id * 3 + 1] = (vehicles.velocity[id * 3 + 1] ?? 0) + (WILDCAT_JUMP_IMPULSE_PER_MASS * mass) / mass;
  vehicles.energy[id] = (vehicles.energy[id] ?? 0) - WILDCAT_JET_ENERGY_DRAIN;
}

export function stepWildcat(world: World, id: number, input: PlayerInput, dt: number): void {
  const vehicles = world.vehicles;
  applyWildcatSteering(vehicles, id, input, dt);
  applyWildcatThrust(vehicles, id, input, dt);
  applyWildcatJump(vehicles, id, input);
  applyHoverSpring(world, vehicles, id, dt);
  const base = id * 3;
  vehicles.position[base] = (vehicles.position[base] ?? 0) + (vehicles.velocity[base] ?? 0) * dt;
  vehicles.position[base + 1] = (vehicles.position[base + 1] ?? 0) + (vehicles.velocity[base + 1] ?? 0) * dt;
  vehicles.position[base + 2] = (vehicles.position[base + 2] ?? 0) + (vehicles.velocity[base + 2] ?? 0) * dt;
}

import { raycastInteriors, resolveSphereAgainstInteriors } from './interiors.js';
import { applyVehicleDamage } from './vehicles.js'; // self-import removed in the real file -- see note below

function applyCollisionDamage(world: World, id: number, impactSpeed: number): void {
  const data = VEHICLE_DATA[world.vehicles.kind[id] as VehicleKind];
  if (impactSpeed <= data.collDamageThresholdVel) return;
  applyVehicleDamage(world, id, (impactSpeed - data.collDamageThresholdVel) * data.collDamageMultiplier, -1);
}

export function resolveVehicleCollision(world: World, id: number, previousPosition: Vec3, dt: number): void {
  const vehicles = world.vehicles;
  const kind = vehicles.kind[id] as VehicleKind;
  const data = VEHICLE_DATA[kind];
  const base = id * 3;
  const current: Vec3 = {
    x: vehicles.position[base] ?? 0,
    y: vehicles.position[base + 1] ?? 0,
    z: vehicles.position[base + 2] ?? 0,
  };
  const speed = Math.hypot(
    (current.x - previousPosition.x) / dt,
    (current.y - previousPosition.y) / dt,
    (current.z - previousPosition.z) / dt,
  );

  const ground = sampleTerrain(world.terrain, current.x, current.z).height;
  let hitSomething = false;
  if (current.y - data.checkRadius < ground) {
    vehicles.position[base + 1] = ground + data.checkRadius;
    if ((vehicles.velocity[base + 1] ?? 0) < 0) vehicles.velocity[base + 1] = 0;
    hitSomething = true;
    // Ground impact is its own, separately-cited rule from the generic object-collision one.
    if (speed > data.groundImpactMinSpeed) {
      applyVehicleDamage(world, id, (speed - data.groundImpactMinSpeed) * data.groundImpactSpeedDamageScale, -1);
    }
  }

  // raycastInteriors takes a normalized direction and a scalar distance, not a second point --
  // mirrors movement.ts's own sweepChest helper exactly (the M4 round-1 fix for player/
  // force-field tunnelling), reused here instead of reinvented for the same reason a fast
  // vehicle can cross a thin wall within one 32 ms tick without either endpoint overlapping it.
  const sweepDx = current.x - previousPosition.x;
  const sweepDy = current.y - previousPosition.y;
  const sweepDz = current.z - previousPosition.z;
  const sweepLength = Math.hypot(sweepDx, sweepDy, sweepDz);
  const interiorHit =
    sweepLength > 0
      ? raycastInteriors(
          world.interiors,
          previousPosition,
          { x: sweepDx / sweepLength, y: sweepDy / sweepLength, z: sweepDz / sweepLength },
          sweepLength,
        )
      : null;
  if (interiorHit) {
    vehicles.position.set([interiorHit.point.x, interiorHit.point.y, interiorHit.point.z], base);
    vehicles.velocity.set([0, 0, 0], base);
    hitSomething = true;
  }
  const sphereResolved = resolveSphereAgainstInteriors(world.interiors, current, data.checkRadius);
  if (sphereResolved) {
    vehicles.position.set([sphereResolved.x, sphereResolved.y, sphereResolved.z], base);
    hitSomething = true;
  }

  if (hitSomething) applyCollisionDamage(world, id, speed);
}

const wasUseHeld = new Map<number, boolean>(); // Ours: private edge-detect state, not on PlayerStore -- see Global Constraints

function seatPosition(vehicles: VehicleStore, id: number): Vec3 {
  const base = id * 3;
  return {
    x: vehicles.position[base] ?? 0,
    y: vehicles.position[base + 1] ?? 0,
    z: vehicles.position[base + 2] ?? 0,
  };
}

function tryMountOrDismount(world: World, playerId: number, input: PlayerInput): void {
  const wasHeld = wasUseHeld.get(playerId) ?? false;
  const edge = input.use && !wasHeld;
  wasUseHeld.set(playerId, input.use);
  if (!edge) return;

  const players = world.players;
  const vehicles = world.vehicles;
  const currentVehicle = players.mountedVehicleId[playerId] ?? -1;
  if (currentVehicle !== -1) {
    vehicles.driverId[currentVehicle] = -1;
    players.mountedVehicleId[playerId] = -1;
    return;
  }

  const pBase = playerId * 3;
  const playerPos: Vec3 = { x: players.position[pBase] ?? 0, y: players.position[pBase + 1] ?? 0, z: players.position[pBase + 2] ?? 0 };
  for (let vId = 0; vId < vehicles.count; vId += 1) {
    if (!vehicles.active[vId] || vehicles.destroyed[vId] || vehicles.driverId[vId] !== -1) continue;
    const data = VEHICLE_DATA[vehicles.kind[vId] as VehicleKind];
    const vPos = seatPosition(vehicles, vId);
    const dist = Math.hypot(playerPos.x - vPos.x, playerPos.y - vPos.y, playerPos.z - vPos.z);
    if (dist <= data.minMountDist) {
      vehicles.driverId[vId] = playerId;
      players.mountedVehicleId[playerId] = vId;
      return; // player-id iteration order in stepVehicles's caller already resolves row 13's race
    }
  }
}

function dismountWithoutDamage(world: World, vId: number): void {
  const driverId = world.vehicles.driverId[vId];
  if (driverId === -1) return;
  world.players.mountedVehicleId[driverId] = -1;
  world.vehicles.driverId[vId] = -1;
}

export function stepVehicles(world: World, inputs: Map<number, PlayerInput>, dt: number): void {
  const vehicles = world.vehicles;

  // Resolve mount/dismount requests in ascending player-id order -- deterministic, and
  // resolves failure-matrix row 13 (first claimant wins) without extra bookkeeping, since
  // `tryMountOrDismount` marks a vehicle's driverId the instant it succeeds and every later
  // id in this same loop sees that vehicle as already occupied.
  const ids = [...inputs.keys()].sort((a, b) => a - b);
  for (const playerId of ids) {
    if (!world.players.active[playerId]) continue;
    tryMountOrDismount(world, playerId, inputs.get(playerId) as PlayerInput);
  }

  for (let vId = 0; vId < vehicles.count; vId += 1) {
    if (!vehicles.active[vId]) continue;
    if (vehicles.destroyed[vId]) {
      dismountWithoutDamage(world, vId); // row 5: pad-respawn or Task 7 destruction, no damage here
      continue;
    }
    const driverId = vehicles.driverId[vId];
    const input = driverId !== -1 ? (inputs.get(driverId) ?? idleVehicleInput()) : idleVehicleInput();
    const previous = seatPosition(vehicles, vId);
    if (vehicles.kind[vId] === VehicleKind.Shrike) stepShrike(world, vId, input, dt);
    else stepWildcat(world, vId, input, dt);
    resolveVehicleCollision(world, vId, previous, dt);

    if (driverId !== -1 && world.players.active[driverId]) {
      const seat = seatPosition(vehicles, vId);
      world.players.position.set([seat.x, seat.y, seat.z], driverId * 3);
      world.players.velocity.set([0, 0, 0], driverId * 3);
    }
  }
}

function idleVehicleInput(): PlayerInput {
  return { moveX: 0, moveZ: 0, yaw: 0, pitch: 0, jump: false, jet: false, fire: false, altFire: false, slot: 0, use: false };
}

function tryFireShrikeBlaster(world: World, vId: number, input: PlayerInput, dt: number): void {
  const vehicles = world.vehicles;
  vehicles.weaponTimer[vId] = Math.max(0, (vehicles.weaponTimer[vId] ?? 0) - dt);

  const origin: Vec3 = { x: vehicles.position[base] ?? 0, y: vehicles.position[base + 1] ?? 0, z: vehicles.position[base + 2] ?? 0 };

}

import { applyDamage } from './damage.js';
import { armorFor } from './armor.js';
import { nextRandom } from './random.js';

function ejectPilot(world: World, vehicleId: number): void {
  const driverId = world.vehicles.driverId[vehicleId];
  if (driverId === -1 || !world.players.active[driverId]) return;
  const armor = armorFor(world, driverId);
  const rand = () => nextRandom(world.random);
  // vehicles/vehicle.cs:255-260 -- real impulse magnitudes, converted to a velocity change
  // by dividing by mass, matching Torque's own applyImpulse convention (see this plan's
  // numbers table for why this is an adaptation, not a direct port).
  const impulse: Vec3 = {
    x: 250 - rand() * 500,
    y: 250 - rand() * 500,
    z: rand() * 100 + 50,
  };
  const base = driverId * 3;
  world.players.velocity[base] = (world.players.velocity[base] ?? 0) + impulse.x / armor.mass;
  world.players.velocity[base + 2] = (world.players.velocity[base + 2] ?? 0) + impulse.y / armor.mass;
  world.players.velocity[base + 1] = (world.players.velocity[base + 1] ?? 0) + impulse.z / armor.mass;
  world.players.mountedVehicleId[driverId] = -1;
  world.vehicles.driverId[vehicleId] = -1;
  applyDamage(world, driverId, 0.4, -1, armor); // vehicles/vehicle.cs:260
}

export function applyVehicleDamage(world: World, id: number, amount: number, attackerId: number): void {
  const vehicles = world.vehicles;
  if (amount <= 0 || !vehicles.active[id] || vehicles.destroyed[id]) return;
  const data = VEHICLE_DATA[vehicles.kind[id] as VehicleKind];
  const energy = vehicles.energy[id] ?? 0;
  const perPoint = data.energyPerDamagePoint;
  const spentFromShield = perPoint > 0 ? Math.min(energy / perPoint, amount) : 0;
  vehicles.energy[id] = energy - spentFromShield * perPoint;
  const remaining = amount - spentFromShield;
  vehicles.damage[id] = Math.min((vehicles.damage[id] ?? 0) + remaining, data.maxDamage);
  if ((vehicles.damage[id] ?? 0) < data.maxDamage) return;
  vehicles.destroyed[id] = 1;
  const base = id * 3;
  world.pendingVehicleDestroyed.push({
    id,
    position: { x: vehicles.position[base] ?? 0, y: vehicles.position[base + 1] ?? 0, z: vehicles.position[base + 2] ?? 0 },
    team: vehicles.team[id] ?? 0,
  });
  ejectPilot(world, id);
}

## Spec gaps

- **The AA barrel's real heat-seeking behavior (`isSeeker`, `seekRadius`, `maxSeekAngle`, `seekTime`, `minSeekHeat`) is not modeled.** This plan's shot is a straight tracer, matching every other turret's own "instant tracking, not slew-limited" simplification M4 already established as this project's bar for turret firing. A seeking projectile that curves toward a moving Shrike would be measurably more T2-accurate and is real future work, not attempted here because it is a materially different projectile-integration shape than anything `projectiles.ts` currently has.
- **The Wildcat's jump is a genuine invention, not a T2 mechanic.** The real `HoverVehicleData` defines no jump force at all — only the hover spring and horizontal thrust. The scope this milestone was given explicitly names "jump" for the hover vehicle, so this plan adds one, sized by analogy to the player's own `jumpForce = 8.3 × mass` shape and gated by the same boost energy the real script's afterburner already uses, and says so plainly here rather than presenting it as sourced.
- **Vehicle-vs-player collision (being run over) is out of scope.** The real T2 script has ground/object impact damage rules for a vehicle hitting terrain or another *vehicle*, but this plan does not extend `movement.ts`'s player collision pass to treat a vehicle's hitbox as a pushable/damaging obstacle for a pedestrian player. A Shrike or Wildcat can currently fly or drive through a player's capsule with no interaction. Worth a follow-up task, not attempted here because `movement.ts`'s own collision pass (M4's interior/force-field work) was already a full task's worth of scope and this milestone's own budget is already large.
- **Vehicle kills do not credit a score.** `applyVehicleDamage` accepts `attackerId` for signature symmetry with `applyDamage`/`applyBaseObjectDamage` but this plan does not wire a score change or kill-feed `EventKind` for destroying an enemy vehicle, nor for a vehicle's blaster/AA-barrel shot killing a player (that path already reuses the existing player-damage/score pipeline via `applyDamage`, so *that* half works; only "credit for destroying the vehicle itself" is missing). The spec's own CTF numbers table names player-kill/capture/touch scoring but says nothing about vehicle-destruction scoring, so this is a real gap in the spec, not just an implementation shortcut — a reviewer should decide the number before a follow-up task adds it.
- **The vehicle pad's own real T2 "removable vehicle types per pad" data (`scoutVehicle`/`assaultVehicle`/`mobileBaseVehicle`/`scoutFlyer`/`bomberFlyer`/`hapcFlyer` flags on `StationVehiclePad::createStationVehicle`, `station.cs:747-758`) is not modeled — this milestone's pad menu always offers both Shrike and Wildcat with no per-pad restriction, since Katabatic's own mission data (not re-parsed in this session for this specific field) is assumed to enable both at every pad, matching the spec's own base description, which lists one generic "vehicle pad" per base with no stated restriction.
- **Twin-barrel alternation for both the Shrike blaster and the AA barrel is a single-timer simplification**, stated already in the numbers table but repeated here as a spec gap because it is a visible cosmetic difference (T2's blaster/AA visibly alternates which barrel fires) that a player who knows the real game will notice; the client's muzzle-flash effect (not detailed in this plan) can still alternate its *visual* origin between two mount points per shot without the sim needing two timers, which is the cheap fix a follow-up could make without touching `sim` at all.
- **Vehicle-originated shots inherit two already-tracked M4 gaps rather than fixing them.** The Shrike blaster and a vehicle-targeting AA barrel shot both use `ownerId: -1`, which reproduces issue #15 (a `-1` `ownerId` wraps to `65535` through the wire's unsigned u16 encode/decode) for the same structural reason a ground-turret shot already does. Separately, issue #21 (Laser Rifle hitscan never checks base-object/turret structure occlusion, live or lag-compensated) is a pre-existing gap this plan does not extend to vehicles either way — a Laser Rifle shot that should be blocked by an intact generator will also not be blocked by a vehicle body, matching the existing bug's scope rather than growing it. Neither is fixed here; both are pointed at their existing tracked issues rather than re-described as new findings.
- **`TurretStore.targetKind` (Task 8) is new turret state a client never sees.** It exists purely to disambiguate `targetId`'s referent for server-side aiming and is mixed into `hashWorld` (Task 9) for determinism, but is not added to `TurretSnapshotData`/the wire — a client has no way to tell from a snapshot alone whether a turret is tracking a player or a vehicle, only that it is tracking `targetId`. This matches M4's own precedent of keeping some turret internals (e.g. `timer`) off the wire and is not needed for this milestone's own scope (the client renders turret aim from `state`/`targetId` only, not `targetKind`), but a future commander-map or spectator feature that wants to show "turret X is engaging vehicle Y" specifically would need to add it.
