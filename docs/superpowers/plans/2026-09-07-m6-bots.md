# Milestone 6: Bots Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `packages/bots` stops being a placeholder and drives every seat the server does not have a real WebSocket client for. A bot produces the exact same `PlayerInput` a human sends: it steers toward a goal along a coarse waypoint graph seeded from Katabatic's spawn points, flag stands, and base-object positions, skis downhill and jets uphill the way a human would, spots a living enemy in line of sight and engages at weapon range with a one-step velocity lead, backs off to a friendly inventory station when health or energy runs low, and plays CTF: push toward the enemy flag, carry it home, or hold near the team's own flag and escort a teammate who is carrying the enemy one. The server keeps both teams filled toward 16 a side as humans join and leave, always by adding or removing bots, never by touching a human's seat. `--bots N` still means what it did in M2 through M5 — it is the number of bot slots available at startup — but those slots now run real decisions every tick instead of standing idle. A debug-overlay row shows each team's bot count and, per bot, one of three states (idle, attack, defend). A headless server-side test runs a bot-only 16v16 match for a few thousand ticks and asserts the match actually produces a kill or a flag capture, not just that it doesn't crash. `packages/sim` gains nothing this milestone: every bot decision is read-only over the sim's already-exported API. A bot triggers exactly one sim action directly, a station heal/reload (`applyLoadoutRequest`, a real exported function called for that exact purpose). Mounting an existing unoccupied vehicle is not a second direct call — it has no directly-callable sim function at all — but a wire-bit decision: a bot sets `PlayerInput.use = true` (querying `canSendVehicleUse`, real and exported, to decide when) exactly as a human holding E does, and `stepWorld`'s own `stepVehicles` does the actual mounting on its next pass. Neither path adds new sim surface.
**Architecture:** `packages/bots` grows from an empty placeholder into five focused modules — `waypoints.ts` (graph build + Dijkstra), `perception.ts` (enemy/threat/heal-need scans), `combat.ts` (weapon choice, lead, aim), `steering.ts` (path-follow to `PlayerInput`, world-to-local move-vector math, slope-based ski/jet), and `brain.ts` (the per-tick decision: CTF role, state, and the one call into `steerToward`/`combat` that produces this tick's `PlayerInput`) — plus `vehicles.ts`, a normal typed dependency on `packages/sim/src/vehicles.ts`'s real, merged `VehicleStore`/`VehicleKind`/`MOUNT_RANGE`/`canSendVehicleUse`. **Reconciliation note (this pass, M5 merged as `fb3599a`):** Task 7 was originally written as a runtime feature-detection shim against M5's still-unmerged plan document. M5 has since merged with real code, so Task 7 below is rewritten to import the real types directly, the same way Tasks 1-6 already do — a feature-detection shim would now be needless indirection against code that has existed on `main` the whole time this reconciliation pass ran. None of this touches a single file in `packages/sim`. `packages/server` gains `bots.ts` (a `BotManager`: owns the bot id set, per-bot runtime memory, the waypoint graph built once from the loaded scene, and `rebalanceTeams`, called after every join and disconnect to keep each team topped up toward 16 within the `--bots` budget) and wires `stepBotManager`'s output into `net.ts`'s existing `collectTickInputs` map before `stepWorld` runs. `packages/protocol` adds one small, purely additive `WorldExtras.bots` array (`{ playerId, state }`, bounds-checked like every other snapshot array) so the client's debug overlay can show bot state without the sim needing to know bots exist at all. `packages/client` adds one debug-overlay row. No `PROTOCOL_VERSION` bump — see Global Constraints for why this one wire addition doesn't need one.
**Tech Stack:** the milestone 4/5 stack unchanged — no new dependency in any package beyond `@clans/sim` becoming a real (not just implied) dependency of `@clans/bots`.

## Global Constraints

- **`packages/sim` is untouched by this milestone, not "touched only if unavoidable."** Every sim function a bot needs already exists and is already exported through `packages/sim/src/index.ts` (see the Baseline list above). A bot's only direct sim call is `applyLoadoutRequest` for healing/reloading at a station, the same call the client's own single-player code path already makes. Mounting a vehicle is not a second direct call — real `vehicles.ts` has no exported mount function; it is a wire-bit decision (`PlayerInput.use`, checked against `canSendVehicleUse`) that `stepVehicles` itself resolves every tick, the same path a human's own held-E input takes. Nothing about bot existence, bot state, bot role, or bot decisions needs to be deterministic-replayable, hashed, or snapshotted the way sim state is: a bot is a second, independent input source feeding the same `PlayerInput` channel a human's socket feeds, and the sim cannot tell the two apart, by design (the spec's own words: "the sim does not know the difference"). Bot *runtime memory* (current path, role, aim jitter seed, last decision) therefore lives in `packages/server`'s `BotManager`, in plain JS objects, never in `World`.
- **`--bots N`'s meaning does not change from a caller's point of view, even though its implementation does.** Today, `N` is spawned once at startup and then stands idle forever. After this milestone, `N` is still validated identically (`cli.ts` untouched) and still produces `N` bot-controlled players *at startup* (`smallerTeam`-balanced, exactly as `addBots` does today) — the only difference a running server adds is that `rebalanceTeams` (Task 8) may later remove some of those `N` bots to make room for a joining human, or bring some of them back when a human leaves, always staying within the same `N`-bot budget the flag already promised. `--bots 0` still means "no bots, ever." A reviewer comparing `clans-server --bots 31 --port 7777`'s behavior before and after this milestone sees the same startup player count and the same flag contract; the bots just stop standing still.
- **Team balancing targets `TARGET_TEAM_SIZE = 16` per team (the spec's own "16 versus 16"), never exceeds it, and is driven only by join/leave events, never by a per-tick poll.** `rebalanceTeams` runs exactly twice per network event — once after `handleJoin` successfully adds a human player, once after `handleClose`/`handleMessage`'s disconnect path removes one — never inside the tick loop itself, so it costs nothing on the 999 ticks out of 1000 where team membership hasn't changed. It adds a bot to a team only while `humans + bots < TARGET_TEAM_SIZE` on that team **and** the manager's remaining bot budget (`maxBots − currentBotCount`, where `maxBots` is `ServerOptions.bots`) is greater than zero; it removes a bot from a team only when a human joining that team would push `humans + bots` over `TARGET_TEAM_SIZE`, in which case exactly one bot (lowest score, tie-broken by highest player id — the newest, least-established bot) is removed first, before the human's join is counted against the cap. A team can therefore end a rebalance below 16 (not enough bot budget or not enough humans) but never above it.
- **`WorldExtras.bots` is purely additive and does not bump `PROTOCOL_VERSION`.** It is the last field `writeExtras`/`readExtras` handle, following every existing array; a client build that predates this milestone simply never reads those trailing bytes (nothing is decoded after `extras` in a snapshot message), and this server/client pair is always deployed together in this single-repo demo, unlike a public multiservice API where cross-version compatibility would matter. M4 already established the precedent of adding `WorldExtras` arrays with no version bump (`baseObjects`, `turrets`); this plan follows it. If M5 lands first and bumps `PROTOCOL_VERSION` to 3 for its own, larger wire change, this milestone's field rides on top of that as a further additive change, still with no additional bump.
- **A bot's `PlayerInput.yaw` is not "look direction," it's "the frame `moveX`/`moveZ` are resolved in," and combat aim and movement steering share exactly one yaw value per tick, matching how a human's own mouse-look and WASD share one.** `steering.ts`'s `worldDirectionToLocalMove(direction, yaw)` (Task 3) is the one place this plan converts a world-space desired-movement vector into the yaw-relative `moveX`/`moveZ` pair `movement.ts` expects, so a bot can face (and shoot) an enemy while still strafing toward its path goal, the same way a real player circle-strafes. There is no separate "look controller" and "move controller" — one function in `brain.ts` (Task 6) decides the tick's `yaw` (aim at a target if engaging, else face the next waypoint) and feeds that same `yaw` into both the movement projection and the fire-direction check.
- **Every ESLint `complexity: 10` / `max-depth: 3` budget holds.** `brain.ts`'s per-tick decision is deliberately split into small, named, single-purpose functions (`decideRole`, `decideGoal`, `decideState`, `decideCombat`, `composeInput`) rather than one large `stepBot` with branches inline — mirroring the pattern `movement.ts`'s own `classify`/`applyForces`/`writeState` split already established for this codebase.
- **Bots never call `spawnVehicleAtPad` (M5's own future function).** Two players (or a player and a bot) racing for the same pad is already a real edge case M5's own failure matrix names for two *humans*; adding a bot into that contention on the server's own initiative — with no UI feedback if it "steals" a pad slot a human was about to use — is a worse experience than a bot simply not doing it. A bot only ever mounts a vehicle that already exists, is unoccupied (`driverId === -1`), and is within its own waypoint-graph reach — see Task 7 and Spec gaps.
- **Bot decision cost is bounded and tested, not assumed cheap.** Per bot per tick: one `O(players)` enemy scan (≤ 32, each a `hasLineOfSight` terrain march), one `O(baseObjects)` nearest-station scan when healing is needed (≤ 64, most ticks skipped entirely once `needsHealing` is false), and, only when the bot has no current path or has reached its next waypoint, one Dijkstra pass over the waypoint graph (≤ ~40 nodes for Katabatic — see Task 2's node count). Task 11's bench test asserts 32 bots' worth of this, every tick, for 5000 ticks, stays under the sim's own 32 ms tick budget on the same machine class M2's existing prediction/bench tests already run on.

## Numbers this plan picks ("ours")

| Number | Value | Why | Where |
|---|---|---|---|
| `TARGET_TEAM_SIZE` | 16 | Spec's own "16 versus 16" — cited, not picked, but restated here since every rebalancing number in this table is sized against it | Task 8 |
| `K_NEAREST` (waypoint graph, nearest-neighbor edges per node) | 4 | Guarantees a connected-ish base graph regardless of node spacing before the threshold/merge passes run; small enough that a ~40-node graph stays a few hundred edges, not the ~800 a full mesh would need | Task 2 |
| `WAYPOINT_EDGE_MAX_DISTANCE` | 300 m | Dense, short-range edges between landmarks that sit close together (a base's own generators/stations/pad cluster tightly); long inter-base hops are covered by `K_NEAREST` and the component-merge pass, not this threshold | Task 2 |
| `WAYPOINT_REACHED_RADIUS` | 4 m | "Close enough to call a waypoint reached" — sized like M5's own `MOUNT_RANGE`/`VEHICLE_PAD_USE_RADIUS` picks (both 4 m), reused for consistency rather than inventing a different scale | Task 3 |
| `STUCK_CHECK_TICKS` | 60 (≈1.92 s at the 32 ms tick) | Long enough that normal ski/run deceleration on a slope never falsely triggers it; short enough that a bot wedged against geometry recovers well within a human's patience | Task 3 |
| `STUCK_MIN_PROGRESS` | 1 m | A bot that has moved less than this toward its goal over `STUCK_CHECK_TICKS` is not making meaningful progress, even accounting for skiing's own lateral wobble | Task 3 |
| `VISION_RANGE` | 150 m | The spec gives no bot sensor range; picked well under the Laser Rifle's 1000 m hitscan max (a bot "noticing" an enemy from a kilometer away reads as omniscient, not alert) and comfortably above every other weapon's own effective range | Task 4 |
| `CLOSE_RANGE` (Chaingun preferred inside this, Spinfusor/Blaster preferred beyond it) | 25 m | Splash-radius safety margin for the Spinfusor (7.5 m radius) plus room for the Chaingun's own tracer travel time to matter; not a T2 script number, since T2 weapon choice was a human's own judgment call, not a datablock field | Task 5 |
| `MORTAR_MIN_RANGE` (Heavy bots only, opportunistic) | 40 m | Keeps a bot from mortaring a target close enough that the 20 m blast radius would as likely catch the bot itself | Task 5 |
| `AIM_TOLERANCE_DEG` | 4° | Fires once the lead point sits within this cone of the bot's current aim, matching a human's own imprecision at typical FOV/mouse-sensitivity settings, not a hitscan-perfect aimbot | Task 5 |
| `AIM_JITTER_DEG` | ±2°, applied once per fresh target acquisition (not re-rolled every tick) | Prevents perfectly repeatable aim between otherwise-identical engagements without needing a difficulty setting (out of scope this milestone, per the given scope) | Task 5 |
| `LOW_HEALTH_FRACTION` | 0.4 | Below 40% health a bot breaks off to heal rather than pressing an engagement it is likely to lose | Task 4 |
| `LOW_ENERGY_FRACTION` | 0.3 | Below 30% energy a bot can no longer jet/ski effectively over Katabatic's terrain and heads to a station | Task 4 |
| `DEFENDER_FRACTION` | 0.25 | One in four of a team's bots holds home/escort duty; the rest push offense — biased toward offense on purpose, since the milestone's own e2e proof (Task 11) needs captures or kills to actually happen within a bounded tick count, and an all-defensive bot team would stalemate | Task 1 |
| `DEFEND_ENGAGE_RADIUS` | 120 m | How far a defender will chase an intruder away from its own flag stand before turning back — keeps a defender from being pulled across the whole map by a feint | Task 6 |

```ts
import type { RandomState } from '@clans/sim';

export enum BotState {
  Idle = 0,
  Attack = 1,
  Defend = 2,
}

export enum BotRole {
  Attacker = 0,
  Defender = 1,
}

export const DEFENDER_FRACTION = 0.25; // Ours — see this plan's "ours" numbers table.

export interface BotRuntimeState {
  playerId: number;
  role: BotRole;
  state: BotState;
  /** The current waypoint path, world-space x/z only (y is sampled fresh from terrain
   *  each tick by steering.ts, since a stored y can go stale if a base object or a
   *  destroyed structure changes the ground under a queued waypoint). */
  path: Array<{ x: number; z: number }>;
  pathIndex: number;
  /** A cheap key identifying what goal produced `path` (e.g. `flag:1` or `station:4`),
   *  so steering.ts/brain.ts can tell "still the same goal" apart from "goal changed,
   *  repath" without diffing the path array itself. */
  goalKey: string | null;
  aimYaw: number;
  /** Rolled once per fresh target acquisition, not every tick — see combat.ts. */
  aimJitterDeg: number;
  engagedTargetId: number; // -1 = none
  stuckBaselinePosition: { x: number; z: number };
  stuckBaselineTick: number;
  random: RandomState;
}

export function createBotRuntimeState(
  playerId: number,
  role: BotRole,
  seed: number,
): BotRuntimeState {
  return {
    playerId,
    role,
    state: BotState.Idle,
    path: [],
    pathIndex: 0,
    goalKey: null,
    aimYaw: 0,
    aimJitterDeg: 0,
    engagedTargetId: -1,
    stuckBaselinePosition: { x: 0, z: 0 },
    stuckBaselineTick: 0,
    random: { value: seed || 1 },
  };
}

/** Deterministic in input order: the first `defenderCount` ids (by array order, not by
 *  numeric id) become Defenders. Callers that want a stable assignment across a
 *  rebalance should pass ids in a stable order (e.g. ascending by id) themselves —
 *  this function does not sort, so re-ordering the input re-assigns roles. */
export function assignRoles(
  botIds: readonly number[],
  defenderFraction = DEFENDER_FRACTION,
): Map<number, BotRole> {
  const roles = new Map<number, BotRole>();
  const defenderCount = Math.min(botIds.length, Math.round(botIds.length * defenderFraction));
  botIds.forEach((id, index) => {
    roles.set(id, index < defenderCount ? BotRole.Defender : BotRole.Attacker);
  });
  return roles;
}
```

```ts
import { activeForceFieldBlockers, hasLineOfSight, type Vec3, type World } from '@clans/sim';

export interface WaypointNode {
  id: number;
  position: Vec3;
  label: string;
}

export interface WaypointGraph {
  nodes: WaypointNode[];
  edges: Map<number, number[]>;
}

const K_NEAREST = 4; // Ours.
const WAYPOINT_EDGE_MAX_DISTANCE = 300; // Ours, meters.

function distance(a: Vec3, b: Vec3): number {
  return Math.hypot(a.x - b.x, a.y - b.y, a.z - b.z);
}

function addEdge(edges: Map<number, number[]>, a: number, b: number): void {
  const listA = edges.get(a) ?? [];
  if (!listA.includes(b)) listA.push(b);
  edges.set(a, listA);
  const listB = edges.get(b) ?? [];
  if (!listB.includes(a)) listB.push(a);
  edges.set(b, listB);
}

function connectedComponents(nodeCount: number, edges: Map<number, number[]>): number[][] {
  const seen = new Uint8Array(nodeCount);
  const components: number[][] = [];
  for (let start = 0; start < nodeCount; start += 1) {
    if (seen[start]) continue;
    const component: number[] = [];
    const queue = [start];
    seen[start] = 1;
    while (queue.length > 0) {
      const id = queue.pop() as number;
      component.push(id);
      for (const next of edges.get(id) ?? []) {
        if (!seen[next]) {
          seen[next] = 1;
          queue.push(next);
        }
      }
    }
    components.push(component);
  }
  return components;
}

/** Repeatedly connects the two closest nodes across the two closest components until
 *  only one component remains -- guarantees connectivity regardless of how the
 *  landmarks are actually distributed on a given map, rather than gambling on a single
 *  distance threshold covering every real gap (failure matrix row 15). */
function mergeComponents(nodes: WaypointNode[], edges: Map<number, number[]>): void {
  let components = connectedComponents(nodes.length, edges);
  while (components.length > 1) {
    let bestA = -1,
      bestB = -1,
      bestDist = Infinity;
    for (let ci = 0; ci < components.length; ci += 1) {
      for (let cj = ci + 1; cj < components.length; cj += 1) {
        for (const a of components[ci] as number[]) {
          for (const b of components[cj] as number[]) {
            const d = distance((nodes[a] as WaypointNode).position, (nodes[b] as WaypointNode).position);
            if (d < bestDist) {
              bestDist = d;
              bestA = a;
              bestB = b;
            }
          }
        }
      }
    }
    addEdge(edges, bestA, bestB);
    components = connectedComponents(nodes.length, edges);
  }
}

export function buildWaypointGraph(landmarks: Array<{ position: Vec3; label: string }>): WaypointGraph {
  const nodes: WaypointNode[] = landmarks.map((landmark, id) => ({ id, ...landmark }));
  const edges = new Map<number, number[]>();
  for (let i = 0; i < nodes.length; i += 1) {
    const ranked = nodes
      .map((n, j) => ({ j, d: distance((nodes[i] as WaypointNode).position, n.position) }))
      .filter((entry) => entry.j !== i)
      .sort((a, b) => a.d - b.d);
    for (const entry of ranked.slice(0, K_NEAREST)) addEdge(edges, i, entry.j);
    for (const entry of ranked) {
      if (entry.d <= WAYPOINT_EDGE_MAX_DISTANCE) addEdge(edges, i, entry.j);
    }
  }
  mergeComponents(nodes, edges);
  return { nodes, edges };
}

export function nearestNode(graph: WaypointGraph, position: Vec3): number {
  let best = 0;
  let bestDist = Infinity;
  for (const node of graph.nodes) {
    const d = distance(node.position, position);
    if (d < bestDist) {
      bestDist = d;
      best = node.id;
    }
  }
  return best;
}

/** An edge is blocked this tick if the straight segment between its two nodes crosses a
 *  currently-powered enemy force field. Terrain occlusion is deliberately NOT checked
 *  here -- a bot that has to go up and over a hill to use an edge still benefits from
 *  the sim's own ski/jet movement getting it there, the same as a human taking the same
 *  route; hasLineOfSight is reserved for combat perception (Task 4), not pathing. */
function edgeBlocked(world: World, forTeam: number, a: Vec3, b: Vec3): boolean {
  const blockers = activeForceFieldBlockers(world, forTeam);
  if (blockers.length === 0) return false;
  const dx = b.x - a.x,
    dy = b.y - a.y,
    dz = b.z - a.z;
  const length = Math.hypot(dx, dy, dz);
  if (length === 0) return false;
  // Reuses hasLineOfSight purely as a segment-vs-terrain-height march; force fields are
  // thin vertical quads (baseObjects.ts's forceFieldQuad), so a cheap sampled check along
  // the segment against each blocker's own bounding test is enough for a coarse graph --
  // ours: not a real geometric raycast against the field's InteriorInstance, which would
  // require importing raycastInteriors here and duplicating movement.ts's own sweep. See
  // Spec gaps.
  const steps = Math.max(1, Math.ceil(length / 10));
  for (let i = 0; i <= steps; i += 1) {
    const t = i / steps;
    const point = { x: a.x + dx * t, y: a.y + dy * t, z: a.z + dz * t };
    for (const blocker of blockers) {
      const bx = blocker.position.x,
        bz = blocker.position.z;
      if (Math.hypot(point.x - bx, point.z - bz) < 6) return true; // Ours: field half-width margin.
    }
  }
  return false;
}

interface QueueEntry {
  id: number;
  cost: number;
}

/** Dijkstra, not A* -- the spec's own bots section names A* for a full navmesh; this
 *  plan's graph tops out around 40 nodes for Katabatic (see Task 8's landmark count), so
 *  a heuristic buys nothing measurable and Dijkstra is simpler to get right. See Spec
 *  gaps. */
export function findPath(
  graph: WaypointGraph,
  world: World,
  forTeam: number,
  from: Vec3,
  to: Vec3,
): Vec3[] | null {
  const startId = nearestNode(graph, from);
  const goalId = nearestNode(graph, to);
  const dist = new Map<number, number>([[startId, 0]]);
  const prev = new Map<number, number>();
  const queue: QueueEntry[] = [{ id: startId, cost: 0 }];
  const visited = new Set<number>();
  while (queue.length > 0) {
    queue.sort((a, b) => a.cost - b.cost);
    const current = queue.shift() as QueueEntry;
    if (visited.has(current.id)) continue;
    visited.add(current.id);
    if (current.id === goalId) break;
    for (const neighborId of graph.edges.get(current.id) ?? []) {
      const a = (graph.nodes[current.id] as WaypointNode).position;
      const b = (graph.nodes[neighborId] as WaypointNode).position;
      if (edgeBlocked(world, forTeam, a, b)) continue;
      const cost = current.cost + distance(a, b);
      if (cost < (dist.get(neighborId) ?? Infinity)) {
        dist.set(neighborId, cost);
        prev.set(neighborId, current.id);
        queue.push({ id: neighborId, cost });
      }
    }
  }
  if (!dist.has(goalId)) return null;
  const nodeIds: number[] = [goalId];
  let walk = goalId;
  while (walk !== startId) {
    const p = prev.get(walk);
    if (p === undefined) return null; // Disconnected after all (blocked edges pruned the only route).
    nodeIds.unshift(p);
    walk = p;
  }
  return [from, ...nodeIds.map((id) => (graph.nodes[id] as WaypointNode).position), to];
}
```

```ts
import { sampleTerrain, type ArmorData, type PlayerInput, type Vec3, type World } from '@clans/sim';
import { findPath, nearestNode, type WaypointGraph } from './waypoints.js';
import type { BotRuntimeState } from './types.js';

export const WAYPOINT_REACHED_RADIUS = 4; // Ours.
export const STUCK_CHECK_TICKS = 60; // Ours.
export const STUCK_MIN_PROGRESS = 1; // Ours, meters.

/** Projects a world-space unit direction onto the yaw-relative forward/right frame
 *  movement.ts's own desiredVelocity uses (forward = (sin yaw, 0, cos yaw), right =
 *  (-cos yaw, 0, sin yaw)) -- the inverse of that construction, so a bot can hold a yaw
 *  aimed at an enemy while still strafing toward a waypoint that isn't directly ahead. */
export function worldDirectionToLocalMove(
  direction: Vec3,
  yaw: number,
): { moveX: number; moveZ: number } {
  const sin = Math.sin(yaw);
  const cos = Math.cos(yaw);
  const forwardX = sin,
    forwardZ = cos;
  const rightX = -cos,
    rightZ = sin;
  return {
    moveZ: direction.x * forwardX + direction.z * forwardZ,
    moveX: direction.x * rightX + direction.z * rightZ,
  };
}

/** Ours, simple slope read rather than the spec's own "nav cost function rewards
 *  descent": samples terrain height a short probe distance ahead along the movement
 *  heading and compares it to the current height. Downhill beyond the armor's own
 *  runSurfaceAngle-adjacent slope -> ski (hold jump); steep uphill with energy to spare
 *  -> jet; otherwise neither. */
const SLOPE_PROBE_DISTANCE = 3; // Ours, meters.

export function slopeAssist(
  world: World,
  x: number,
  z: number,
  headingYaw: number,
  energy: number,
  armor: ArmorData,
): { jump: boolean; jet: boolean } {
  const here = sampleTerrain(world.terrain, x, z);
  const aheadX = x + Math.sin(headingYaw) * SLOPE_PROBE_DISTANCE;
  const aheadZ = z + Math.cos(headingYaw) * SLOPE_PROBE_DISTANCE;
  const ahead = sampleTerrain(world.terrain, aheadX, aheadZ);
  if (here.empty || ahead.empty) return { jump: false, jet: false };
  const drop = here.height - ahead.height; // positive = downhill ahead
  if (drop > 0.5) return { jump: true, jet: false };
  if (drop < -1.5 && energy > armor.minJetEnergy * 2) return { jump: false, jet: true };
  return { jump: false, jet: false };
}

/** Resets (and reports false) whenever the goal changed since the last check -- a fresh
 *  goal always gets a fresh baseline, never inherits a stale one from a previous, now-
 *  abandoned goal. Reports true, and immediately resets its own baseline to the CURRENT
 *  tick/position (failure matrix row 17), once STUCK_CHECK_TICKS have passed with less
 *  than STUCK_MIN_PROGRESS of net movement from the baseline. */
export function checkStuck(
  runtime: BotRuntimeState,
  world: Pick<World, 'tick'>,
  currentPosition: Vec3,
): boolean {
  const elapsed = world.tick - runtime.stuckBaselineTick;
  if (elapsed < STUCK_CHECK_TICKS) {
    if (elapsed < 0) {
      runtime.stuckBaselineTick = world.tick;
      runtime.stuckBaselinePosition = { x: currentPosition.x, z: currentPosition.z };
    }
    return false;
  }
  const progress = Math.hypot(
    currentPosition.x - runtime.stuckBaselinePosition.x,
    currentPosition.z - runtime.stuckBaselinePosition.z,
  );
  const stuck = progress < STUCK_MIN_PROGRESS;
  runtime.stuckBaselineTick = world.tick;
  runtime.stuckBaselinePosition = { x: currentPosition.x, z: currentPosition.z };
  return stuck;
}

function ensurePath(
  graph: WaypointGraph,
  world: World,
  team: number,
  runtime: BotRuntimeState,
  from: Vec3,
  goal: Vec3,
  goalKey: string,
): void {
  const needsNewPath =
    runtime.goalKey !== goalKey || runtime.pathIndex >= runtime.path.length || runtime.path.length === 0;
  if (!needsNewPath) return;
  const path = findPath(graph, world, team, from, goal);
  runtime.path = (path ?? [goal]).map((p) => ({ x: p.x, z: p.z }));
  runtime.pathIndex = 0;
  runtime.goalKey = goalKey;
}

/** Advances along the current path, repathing on a stale/exhausted path, a changed
 *  goal, or a detected stall (failure matrix row 17). Returns only movement fields --
 *  yaw is decided once, by brain.ts, shared with combat aim (Global Constraints). */
export function steerToward(
  graph: WaypointGraph,
  world: World,
  team: number,
  runtime: BotRuntimeState,
  botId: number,
  goalPosition: Vec3,
  goalKey: string,
  currentPosition: Vec3,
  armor: ArmorData,
  energy: number,
): Partial<PlayerInput> & { headingYaw: number } {
  ensurePath(graph, world, team, runtime, currentPosition, goalPosition, goalKey);
  if (checkStuck(runtime, world, currentPosition)) {
    runtime.goalKey = null; // forces ensurePath to repath from the bot's actual position next call
    ensurePath(graph, world, team, runtime, currentPosition, goalPosition, goalKey);
  }
  let target = runtime.path[runtime.pathIndex];
  while (
    target &&
    Math.hypot(currentPosition.x - target.x, currentPosition.z - target.z) < WAYPOINT_REACHED_RADIUS &&
    runtime.pathIndex < runtime.path.length - 1
  ) {
    runtime.pathIndex += 1;
    target = runtime.path[runtime.pathIndex];
  }
  if (!target) return { moveX: 0, moveZ: 0, jump: false, jet: false, headingYaw: 0 };
  const dx = target.x - currentPosition.x,
    dz = target.z - currentPosition.z;
  const length = Math.hypot(dx, dz) || 1;
  const direction = { x: dx / length, y: 0, z: dz / length };
  const headingYaw = Math.atan2(direction.x, direction.z);
  const { jump, jet } = slopeAssist(world, currentPosition.x, currentPosition.z, headingYaw, energy, armor);
  const { moveX, moveZ } = worldDirectionToLocalMove(direction, headingYaw);
  return { moveX, moveZ, jump, jet, headingYaw };
}

export { nearestNode };
```

```ts
import {
  armorFor,
  BaseObjectKind,
  hasLineOfSight,
  playerHitbox,
  type World,

export const VISION_RANGE = 150; // Ours.
export const LOW_HEALTH_FRACTION = 0.4; // Ours.
export const LOW_ENERGY_FRACTION = 0.3; // Ours.
const MUZZLE_HEIGHT = 1.6; // weapons.ts's own constant, restated here to avoid a circular
// re-export dependency on weapons.ts internals -- the value is cited, not picked; see
// weapons.ts:53.

function botEye(world: World, botId: number): { x: number; y: number; z: number } {
  const base = botId * 3;
  return {
    x: world.players.position[base] ?? 0,
    y: (world.players.position[base + 1] ?? 0) + MUZZLE_HEIGHT,
    z: world.players.position[base + 2] ?? 0,
  };
}

export function findNearestVisibleEnemy(world: World, botId: number): number | null {
  const team = world.players.team[botId] ?? 0;
  const eye = botEye(world, botId);
  let best: number | null = null;
  let bestDistance = Infinity;
  for (let id = 0; id < world.players.count; id += 1) {
    if (id === botId || !world.players.active[id] || !world.players.alive[id]) continue;
    if (world.players.team[id] === team) continue;
    // Failure matrix row 18, real M5 behavior (projectiles.ts's isValidTarget, weapons.ts:420):
    // a mounted player has no separate hitbox while riding a vehicle -- only the vehicle can
    // be shot. A bot with no vehicle-combat logic this milestone treats a mounted enemy as
    // simply not there, rather than "visible" and then wasting every shot against it.
    if (world.players.mountedVehicleId[id] !== -1) continue;
    const hitbox = playerHitbox(world, id, armorFor(world, id));
    const d = Math.hypot(eye.x - hitbox.center.x, eye.y - hitbox.center.y, eye.z - hitbox.center.z);
    if (d > VISION_RANGE || d >= bestDistance) continue;
    if (!hasLineOfSight(world, eye, hitbox.center)) continue;
    best = id;
    bestDistance = d;
  }
  return best;
}

export function needsHealing(world: World, botId: number): boolean {
  const armor = armorFor(world, botId);
  const health = 1 - (world.players.damage[botId] ?? 0) / armor.maxDamage;
  const energy = (world.players.energy[botId] ?? 0) / armor.maxEnergy;
  return health < LOW_HEALTH_FRACTION || energy < LOW_ENERGY_FRACTION;
}

export function findNearestFriendlyStation(world: World, botId: number): number | null {
  const store = world.baseObjects;
  const team = world.players.team[botId] ?? 0;
  const base = botId * 3;
  const bx = world.players.position[base] ?? 0,
    bz = world.players.position[base + 2] ?? 0;
  let best: number | null = null;
  let bestDistance = Infinity;
  for (let id = 0; id < store.count; id += 1) {
    if (store.kind[id] !== BaseObjectKind.StationInventory) continue;
    if (store.team[id] !== team || !store.powered[id] || store.destroyed[id]) continue;
    const ox = store.position[id * 3] ?? 0,
      oz = store.position[id * 3 + 2] ?? 0;
    const d = Math.hypot(bx - ox, bz - oz);
    if (d < bestDistance) {
      bestDistance = d;
      best = id;
    }
  }
  return best;
}

export function findEscortedCarrier(world: World, team: number, selfId: number): number | null {
  for (let flagId = 0; flagId < world.flags.team.length; flagId += 1) {
    if (world.flags.team[flagId] === team) continue; // only the ENEMY flag has a carrier worth escorting
    const carrierId = world.flags.carrierId[flagId];
    if (
      carrierId === undefined ||
      carrierId < 0 ||
      carrierId === selfId ||
      !world.players.active[carrierId] ||
      !world.players.alive[carrierId] ||
      world.players.team[carrierId] !== team
    ) {
      continue;
    }
    return carrierId;
  }
  return null;
}
```

```ts
import { armorFor, nextRandom, playerHitbox, WeaponId, WEAPON_DATA, type Vec3, type World } from '@clans/sim';
import { ammoIndex } from '@clans/sim'; // re-exported by weapons.ts's star export in index.ts
import type { BotRuntimeState } from './types.js';

export const CLOSE_RANGE = 25; // Ours.
export const MORTAR_MIN_RANGE = 40; // Ours.
export const AIM_TOLERANCE_DEG = 4; // Ours.
export const AIM_JITTER_DEG = 2; // Ours, applied as +/-.

function ammoFor(world: World, botId: number, weaponId: WeaponId): number {
  return world.players.ammo[ammoIndex(botId, weaponId)] ?? 0;
}

/** Spinfusor/Blaster beyond CLOSE_RANGE, Chaingun inside it, Mortar only for a Heavy
 *  bot engaging beyond MORTAR_MIN_RANGE (its own blast radius makes it unsafe closer),
 *  Blaster as the final fallback (ammo is always -1/infinite for it -- weapons.ts's own
 *  resetLoadout convention). Never switches to a weapon with zero ammo. */
export function chooseWeapon(world: World, botId: number, distance: number): WeaponId {
  if (distance > MORTAR_MIN_RANGE && ammoFor(world, botId, WeaponId.Mortar) > 0) {
    return WeaponId.Mortar;
  }
  if (distance > CLOSE_RANGE) {
    if (ammoFor(world, botId, WeaponId.Spinfusor) !== 0) return WeaponId.Spinfusor; // -1 or > 0
  } else if (ammoFor(world, botId, WeaponId.Chaingun) !== 0) {
    return WeaponId.Chaingun;
  }
  if (ammoFor(world, botId, WeaponId.Spinfusor) !== 0) return WeaponId.Spinfusor;
  if (ammoFor(world, botId, WeaponId.Chaingun) !== 0) return WeaponId.Chaingun;
  return WeaponId.Blaster;
}

/** One-step lead: where the target will be after the time this weapon's projectile takes
 *  to cross the CURRENT distance. Not a true ballistic intercept solve (that requires
 *  iterating since the target moves while the shot is in flight, which in turn changes
 *  the intercept time) -- ours, matching the spec's own "close enough for a demo" bar
 *  elsewhere in this codebase. A projectileSpeed of 0 (hitscan) returns the target's
 *  current position unchanged. */
export function leadPosition(
  shooterPosition: Vec3,
  targetPosition: Vec3,
  targetVelocity: Vec3,
  projectileSpeed: number,
): Vec3 {
  if (projectileSpeed <= 0) return targetPosition;
  const distance = Math.hypot(
    shooterPosition.x - targetPosition.x,
    shooterPosition.y - targetPosition.y,
    shooterPosition.z - targetPosition.z,
  );
  const travelTime = distance / projectileSpeed;
  return {
    x: targetPosition.x + targetVelocity.x * travelTime,
    y: targetPosition.y + targetVelocity.y * travelTime,
    z: targetPosition.z + targetVelocity.z * travelTime,
  };
}

function toDeg(radians: number): number {
  return (radians * 180) / Math.PI;
}

export function aimAndFire(
  world: World,
  runtime: BotRuntimeState,
  botId: number,
  targetId: number,
): { yaw: number; pitch: number; fire: boolean } {
  if (runtime.engagedTargetId !== targetId) {
    runtime.engagedTargetId = targetId;
    runtime.aimJitterDeg = (nextRandom(runtime.random) * 2 - 1) * AIM_JITTER_DEG;
  }
  const shooterBase = botId * 3;
  const shooter: Vec3 = {
    x: world.players.position[shooterBase] ?? 0,
    y: world.players.position[shooterBase + 1] ?? 0,
    z: world.players.position[shooterBase + 2] ?? 0,
  };
  const distance = Math.hypot(
    shooter.x - (playerHitbox(world, targetId, armorFor(world, targetId)).center.x),
    0,
    shooter.z - (playerHitbox(world, targetId, armorFor(world, targetId)).center.z),
  );
  const weaponId = chooseWeapon(world, botId, distance);
  const weapon = WEAPON_DATA[weaponId];
  const hitbox = playerHitbox(world, targetId, armorFor(world, targetId));
  const targetBase = targetId * 3;
  const targetVelocity: Vec3 = {
    x: world.players.velocity[targetBase] ?? 0,
    y: world.players.velocity[targetBase + 1] ?? 0,
    z: world.players.velocity[targetBase + 2] ?? 0,
  };
  const lead = leadPosition(shooter, hitbox.center, targetVelocity, weapon.speed);
  const dx = lead.x - shooter.x,
    dy = lead.y - shooter.y,
    dz = lead.z - shooter.z;
  const idealYaw = Math.atan2(dx, dz) + (runtime.aimJitterDeg * Math.PI) / 180;
  const idealPitch = Math.atan2(dy, Math.hypot(dx, dz));
  const aimYaw = runtime.aimYaw;
  const yawErrorDeg = Math.abs(toDeg(Math.atan2(Math.sin(idealYaw - aimYaw), Math.cos(idealYaw - aimYaw))));
  return { yaw: idealYaw, pitch: idealPitch, fire: yawErrorDeg <= AIM_TOLERANCE_DEG };
}
```

```ts
import {
  applyLoadoutRequest,
  armorFor,
  FlagState,
  STATION_USE_RADIUS,
  type PlayerInput,
  type Vec3,
  type World,
} from '@clans/sim';
import { aimAndFire } from './combat.js';
import { findEscortedCarrier, findNearestFriendlyStation, findNearestVisibleEnemy, needsHealing } from './perception.js';
import { steerToward } from './steering.js';
import { BotRole, BotState, type BotRuntimeState } from './types.js';
import type { WaypointGraph } from './waypoints.js';

export const DEFEND_ENGAGE_RADIUS = 120; // Ours.

function playerPoint(world: World, id: number): Vec3 {
  const base = id * 3;
  return {
    x: world.players.position[base] ?? 0,
    y: world.players.position[base + 1] ?? 0,
    z: world.players.position[base + 2] ?? 0,
  };
}

function ownFlagId(world: World, team: number): number {
  for (let id = 0; id < world.flags.team.length; id += 1) if (world.flags.team[id] === team) return id;
  return 0;
}
function enemyFlagId(world: World, team: number): number {
  for (let id = 0; id < world.flags.team.length; id += 1) if (world.flags.team[id] !== team) return id;
  return 1;
}

/** Attacker: carrying the enemy flag -> head home; otherwise -> head to the enemy flag
 *  wherever it currently is (home, dropped, or being carried by a teammate you're about
 *  to catch up to and pass, which is fine -- there's nothing wrong with two teammates
 *  converging on the same flag). Defender: a teammate is carrying the enemy flag ->
 *  escort them; otherwise -> hold near the team's own flag stand. */
function decideGoal(
  world: World,
  runtime: BotRuntimeState,
): { position: Vec3; key: string } {
  const team = world.players.team[runtime.playerId] ?? 0;
  const ownId = ownFlagId(world, team);
  const enemyId = enemyFlagId(world, team);
  if (runtime.role === BotRole.Attacker) {
    if (world.flags.carrierId[enemyId] === runtime.playerId) {
      const base = ownId * 3;
      return {
        position: {
          x: world.flags.standPosition[base] ?? 0,
          y: world.flags.standPosition[base + 1] ?? 0,
          z: world.flags.standPosition[base + 2] ?? 0,
        },
        key: `home:${String(ownId)}`,
      };
    }
    const base = enemyId * 3;
    return {
      position: {
        x: world.flags.position[base] ?? 0,
        y: world.flags.position[base + 1] ?? 0,
        z: world.flags.position[base + 2] ?? 0,
      },
      key: `enemyFlag:${String(enemyId)}`,
    };
  }
  if (world.flags.state[ownId] === FlagState.Dropped) {
    const base = ownId * 3;
    return {
      position: {
        x: world.flags.position[base] ?? 0,
        y: world.flags.position[base + 1] ?? 0,
        z: world.flags.position[base + 2] ?? 0,
      },
      key: `recoverOwn:${String(ownId)}`,
    };
  }
  const carrier = findEscortedCarrier(world, team, runtime.playerId);
  if (carrier !== null) {
    return { position: playerPoint(world, carrier), key: `escort:${String(carrier)}` };
  }
  const base = ownId * 3;
  return {
    position: {
      x: world.flags.standPosition[base] ?? 0,
      y: world.flags.standPosition[base + 1] ?? 0,
      z: world.flags.standPosition[base + 2] ?? 0,
    },
    key: `home:${String(ownId)}`,
  };
}

function decideState(runtime: BotRuntimeState, engagedTargetId: number | null): BotState {
  if (engagedTargetId === null) return BotState.Idle;
  return runtime.role === BotRole.Defender ? BotState.Defend : BotState.Attack;
}

/** A Defender only engages within DEFEND_ENGAGE_RADIUS of its own flag stand; an
 *  Attacker (and a Defender escorting a carrier already away from home) engages any
 *  visible enemy in range with no leash. Row 9: engagedTargetId is re-derived fresh
 *  every call from a live scan, never trusted across ticks, so a target that died or
 *  disconnected between calls simply doesn't come back from findNearestVisibleEnemy. */
function decideCombat(
  world: World,
  runtime: BotRuntimeState,
): { yaw: number; pitch: number; fire: boolean; targetId: number | null } {
  const targetId = findNearestVisibleEnemy(world, runtime.playerId);
  if (targetId === null) {
    runtime.engagedTargetId = -1;
    return { yaw: runtime.aimYaw, pitch: 0, fire: false, targetId: null };
  }
  if (runtime.role === BotRole.Defender) {
    const team = world.players.team[runtime.playerId] ?? 0;
    const homeBase = ownFlagId(world, team) * 3;
    const home = {
      x: world.flags.standPosition[homeBase] ?? 0,
      z: world.flags.standPosition[homeBase + 2] ?? 0,
    };
    const target = playerPoint(world, targetId);
    if (Math.hypot(home.x - target.x, home.z - target.z) > DEFEND_ENGAGE_RADIUS) {
      runtime.engagedTargetId = -1;
      return { yaw: runtime.aimYaw, pitch: 0, fire: false, targetId: null };
    }
  }
  const { yaw, pitch, fire } = aimAndFire(world, runtime, runtime.playerId, targetId);
  return { yaw, pitch, fire, targetId };
}

/** Direct sim call, not a queued wire message (Global Constraints) -- a bot server-side
 *  has no socket, and a station-use decision is a one-shot state change exactly like a
 *  human's own Loadout request, just triggered from here instead of a decoded message. */
function maybeHeal(world: World, botId: number): void {
  if (!needsHealing(world, botId)) return;
  const team = world.players.team[botId] ?? 0;
  const stationId = findNearestFriendlyStation(world, botId);
  if (stationId === null) return;
  const base = botId * 3;
  const stationBase = stationId * 3;
  const dx = (world.players.position[base] ?? 0) - (world.baseObjects.position[stationBase] ?? 0);
  const dz = (world.players.position[base + 2] ?? 0) - (world.baseObjects.position[stationBase + 2] ?? 0);
  if (Math.hypot(dx, dz) > STATION_USE_RADIUS) return;
  applyLoadoutRequest(world, botId, world.players.armor[botId] as never, world.players.hasRepairPack[botId] === 1);
  void team; // team is read above only for symmetry with the rest of this function's own team-scoped calls
}

export function stepBot(world: World, graph: WaypointGraph, runtime: BotRuntimeState): PlayerInput {
  maybeHeal(world, runtime.playerId);
  const goal = decideGoal(world, runtime);
  const armor = armorFor(world, runtime.playerId);
  const energy = world.players.energy[runtime.playerId] ?? 0;
  const team = world.players.team[runtime.playerId] ?? 0;
  const currentPosition = playerPoint(world, runtime.playerId);
  const move = steerToward(
    graph,
    world,
    team,
    runtime,
    runtime.playerId,
    goal.position,
    goal.key,
    currentPosition,
    armor,
    energy,
  );
  const combat = decideCombat(world, runtime);
  const yaw = combat.targetId !== null ? combat.yaw : move.headingYaw;
  runtime.aimYaw = yaw;
  runtime.state = decideState(runtime, combat.targetId);
  return {
    moveX: move.moveX ?? 0,
    moveZ: move.moveZ ?? 0,
    yaw,
    pitch: combat.pitch,
    jump: move.jump ?? false,
    jet: move.jet ?? false,
    fire: combat.fire,
    altFire: false,
    slot: 0,
    packActive: false,
    // Real PlayerInput.use is a required field (M5, packages/sim/src/types.ts:23) -- every
    // bot input must set it, not just a vehicle-aware one, or this object literal fails to
    // typecheck against PlayerInput. Task 6 alone has no vehicle awareness, so this starts
    // false; Task 7 (vehicles.ts, which already modifies brain.ts for decideGoal) revises
    // this single line to `use: shouldUseVehicle(world, runtime, runtime.playerId)` once
    // vehicle piloting exists. Never a queued wire message -- see Global Constraints on why
    // mounting is a PlayerInput bit, not a direct sim call.
    use: false,
  };
}

export function stepBots(
  world: World,
  graph: WaypointGraph,
  runtimes: Map<number, BotRuntimeState>,
): Map<number, PlayerInput> {
  const inputs = new Map<number, PlayerInput>();
  for (const [botId, runtime] of runtimes) {
    if (!world.players.active[botId] || !world.players.alive[botId]) continue;
    inputs.set(botId, stepBot(world, graph, runtime));
  }
  return inputs;
}
```

```ts
import { MOUNT_RANGE, type Vec3, type VehicleStore, type World } from '@clans/sim';
import type { BotRuntimeState } from './types.js';

/** Real M5 mount is permissive about team (vehicles.ts's own findUnoccupiedVehicleInRange
 *  has no team check at all -- any player can mount any unoccupied vehicle). Bots
 *  deliberately narrow this to the bot's own team: the same "don't exploit unintended
 *  permissiveness" policy Global Constraints already states for spawnVehicleAtPad, applied
 *  here to mounting instead of spawning. This is a bot policy choice, not a sim rule. */
function isUsableByTeam(store: VehicleStore, vehicleId: number, team: number): boolean {
  return (
    store.active[vehicleId] === 1 &&
    store.destroyed[vehicleId] === 0 &&
    store.driverId[vehicleId] === -1 &&
    store.team[vehicleId] === team
  );
}

export function findMountableVehicle(world: World, botId: number): number | null {
  const store = world.vehicles;
  const base = botId * 3;
  const bx = world.players.position[base] ?? 0,
    bz = world.players.position[base + 2] ?? 0;
  const team = world.players.team[botId] ?? 0;
  let best: number | null = null;
  let bestDistance = Infinity;
  for (let id = 0; id < store.count; id += 1) {
    if (!isUsableByTeam(store, id, team)) continue;
    const vx = store.position[id * 3] ?? 0,
      vz = store.position[id * 3 + 2] ?? 0;
    const d = Math.hypot(bx - vx, bz - vz);
    if (d <= MOUNT_RANGE && d < bestDistance) {
      bestDistance = d;
      best = id;
    }
  }
  return best;
}

/** Only ever offered as a fallback goal, checked by brain.ts AFTER every CTF priority
 *  (carry home, chase enemy flag, recover own flag, escort a carrier) comes up empty --
 *  a bot never abandons an active CTF task to go joyride a vehicle. See Task 6's
 *  decideGoal and this task's own note in Global Constraints about bots never spawning
 *  a vehicle themselves, only mounting one that already exists. */
export function decideVehicleGoal(
  world: World,
  runtime: BotRuntimeState,
): { position: Vec3; key: string } | null {
  const vehicleId = findMountableVehicle(world, runtime.playerId);
  if (vehicleId === null) return null;
  const base = vehicleId * 3;
  return {
    position: {
      x: world.vehicles.position[base] ?? 0,
      y: world.vehicles.position[base + 1] ?? 0,
      z: world.vehicles.position[base + 2] ?? 0,
    },
    key: `vehicle:${String(vehicleId)}`,
  };
}

/** Feeds Task 6's composeInput: true only once the bot's CURRENT goal is a vehicle goal
 *  (never sent opportunistically just because a vehicle happens to be nearby -- a bot
 *  only presses "E" on the vehicle it actually walked toward) and it is still within
 *  MOUNT_RANGE and still unoccupied by the time the bot arrives -- re-checked fresh every
 *  call, not cached from when the goal was set, so a vehicle taken by a teammate (or
 *  destroyed) in the interim is simply not mounted. Real stepVehicles (vehicles.ts) does
 *  the actual mounting off this bit exactly as it does for a human holding E; this
 *  function only decides whether to send it. */
export function shouldUseVehicle(world: World, runtime: BotRuntimeState, botId: number): boolean {
  if (runtime.goalKey === null || !runtime.goalKey.startsWith('vehicle:')) return false;
  const vehicleId = Number(runtime.goalKey.slice('vehicle:'.length));
  const store = world.vehicles;
  if (Number.isNaN(vehicleId) || vehicleId < 0 || vehicleId >= store.count) return false;
  const team = world.players.team[botId] ?? 0;
  if (!isUsableByTeam(store, vehicleId, team)) return false;
  const base = botId * 3,
    vBase = vehicleId * 3;
  const dx = (world.players.position[base] ?? 0) - (store.position[vBase] ?? 0);
  const dz = (world.players.position[base + 2] ?? 0) - (store.position[vBase + 2] ?? 0);
  return Math.hypot(dx, dz) <= MOUNT_RANGE;
}
```

```ts
}

/** Lowest score first (least-established bot loses its slot), tied by highest player id
 *  (the most recently added bot among equally-low scores). */
function pickBotToRemove(world: World, manager: BotManager, team: number): number | null {
  let best: number | null = null;
  for (const id of manager.botIds) {
    if (!world.players.active[id] || world.players.team[id] !== team) continue;
    if (
      best === null ||
      (world.players.score[id] ?? 0) < (world.players.score[best] ?? 0) ||
      ((world.players.score[id] ?? 0) === (world.players.score[best] ?? 0) && id > best)
    ) {
      best = id;
    }
  }
  return best;
}

function removeBotFromTeam(manager: BotManager, world: World, team: number): boolean {
  const id = pickBotToRemove(world, manager, team);
  if (id === null) return false;
  removePlayer(world, id);
  manager.botIds.delete(id);
  manager.runtimes.delete(id);
  reassignTeamRoles(manager, world, team);
  return true;
}

/** Called after every join/leave (Global Constraints), never on a tick timer. Removes a
 *  bot from a team before it would exceed TARGET_TEAM_SIZE, and backfills a team under
 *  TARGET_TEAM_SIZE from `manager.maxBots`'s remaining budget -- never more, never
 *  fewer than that budget allows (failure matrix rows 12-14). */
export function rebalanceTeams(manager: BotManager, world: World, spawns: SceneSpawn[]): void {
  for (const team of [1, 2]) {
    while (teamCount(world, team) > TARGET_TEAM_SIZE) {
      if (!removeBotFromTeam(manager, world, team)) break; // no bot left to remove -- humans over cap, not this manager's problem
    }
  }
  let remainingBudget = manager.maxBots - manager.botIds.size;
  for (const team of [1, 2]) {
    while (teamCount(world, team) < TARGET_TEAM_SIZE && remainingBudget > 0) {
      addBotToTeam(manager, world, spawns, team);
      remainingBudget -= 1;
    }
  }
}

export function createBotManager(
  world: World,
  spawns: SceneSpawn[],
  landmarks: Array<{ position: Vec3; label: string }>,
  maxBots: number,
): BotManager {
  const manager: BotManager = {
    botIds: new Set(),
    runtimes: new Map(),
    graph: buildWaypointGraph(landmarks),
    maxBots,
    nextSeed: 0,
  };
  rebalanceTeams(manager, world, spawns);
  return manager;
}

export function stepBotManager(manager: BotManager, world: World): Map<number, PlayerInput> {
  return stepBots(world, manager.graph, manager.runtimes);
}

export { smallerTeam };
```

This plan does not implement generator-defense, repair-pack bot usage, or a weighted task-claim system, because none of those are in the given scope's own bullet list — see Spec gaps for the explicit list of what the fuller spec section describes that this plan does not build.
- **Failure-matrix row 18 was substantively wrong in this plan's original draft and is fixed in this pass.** The original row claimed "no bot-side special case is needed" for a mounted enemy, reasoning only about position freshness. Real M5 code (`projectiles.ts`'s `isValidTarget`, `weapons.ts:420`) makes a mounted player's own hitbox permanently un-hittable — only the vehicle can be shot — specifically to stop splash/direct damage from double-dipping a mounted pilot and their vehicle. A bot with the original Task 4 code would find a mounted enemy "visible," aim at it, and fire every tick without ever landing a hit or disengaging. Fixed by excluding `mountedVehicleId !== -1` from `findNearestVisibleEnemy` (Task 4), moving row 18's coverage from Task 7 to Task 4 in the process.
- **Task 12's original draft described a client debug architecture that doesn't exist.** It assumed `debug.ts` already reads a unified `extras` accessor and already has a turret-arc row to copy. Real `NetClient` decodes each `WorldExtras` array into its own field (`projectiles`, `flags`, `baseObjects`, `turrets`, `vehicles` — no unified `extras`), and real `debug.ts` (62 lines, confirmed unchanged from this plan's own citation) has no turret-arc row and reads no snapshot extras at all; every row flows through `stats.ts`'s `describePlayer(world, playerId, stats, extra: DebugExtra)`. Task 12 is rewritten to add a `bots` field to `NetClient` (mirroring the real `vehicles` field's own assignment pattern) and extend `DebugExtra`/`describePlayer` in `stats.ts`, instead of inventing a `debug.ts`-local rendering path.
- **What this session did not verify further:** the exact shape of `loadKatabaticWorld`'s return value beyond `{ world, spawns }` — specifically whether `flagStands`/base-object scene arrays are already available at `packages/server/src/index.ts`'s call site the way Task 9's landmark-building code assumes, or whether they need threading out from inside `loadKatabaticWorld` itself. This plan's Task 9 describes the intent precisely (which scene arrays feed the landmark list) and notes explicitly that it is "the same scene data `createFlags`/`createBaseObjects` were already built from," but the implementer should re-read `packages/server/src/world.ts`'s `loadKatabaticWorld` function body (not read in full in this session — only its top-level imports and `addBots`/`teamCount`/`smallerTeam`/`spawnPointFor`, lines 150-190, were read directly) to confirm the exact accessor before writing Task 9's code, rather than trusting this plan's own guess at the return shape verbatim.

## Spec gaps

- **The spec's own Bots section describes an 8 m-cell heightfield grid with A* for long routes and a full task-claiming system (defend generator, repair, attack flag, escort, pilot, weighted by distance).** The given scope for this milestone explicitly narrows this to a coarse landmark graph and CTF-only behavior (attack/defend/capture), so this plan does not build the fuller spec description — generator defense, in-combat repair-pack usage by a bot, or weighted task claims are all real gaps against the spec's own text, not against this milestone's given scope. Worth a follow-up milestone if the fuller spec behavior is wanted later.
- **Bot loadout is fixed at spawn (Light armor, whatever `addPlayer`'s default already is) with no armor-diversity or loadout-swap strategy.** A bot that uses a station only ever re-requests its own current armor/pack (a pure heal-and-reload), never switches to Medium/Heavy or toggles the Repair Pack. The given scope does not ask for bot loadout strategy, so this is a deliberate simplicity choice, not an oversight — but it does mean every bot in a match plays Light armor, which reads as less varied than a real T2 server. A follow-up could assign armor at bot-creation time the same way `assignRoles` assigns role.
- **`waypoints.ts`'s force-field edge check (`edgeBlocked`) is a coarse point-vs-marched-segment proximity test against each blocker's own center, not a real geometric test against the field's actual `InteriorInstance` quad** (which would require importing `raycastInteriors`/`resolveSphereAgainstInteriors` from `packages/sim` — deliberately avoided so this file's only sim import stays `hasLineOfSight`/`activeForceFieldBlockers`, keeping the pathing layer's sim surface minimal). This can both false-negative (an edge that grazes a field's corner is treated as blocked when it would have cleared) and false-positive (the reverse) at the margins; it is accurate enough to keep a bot from repeatedly slamming into a live field, which is this task's actual goal, but not accurate enough to trust for anything more precise.
- **A bot never repairs a damaged base asset, generator, or teammate, and never deploys a Turret or Sensor pack** (the spec lists both as CTF-adjacent packs but the given scope's own pack line only says "use packs," without specifying which — this plan interprets that narrowly as "use the Repair Pack's own heal/reload path via a station," since that's the only pack behavior the given scope's own combat/CTF description actually implies a bot needs). Broader pack usage (a bot carrying and using a Repair Pack in the field, deploying a Turret/Sensor) is out of scope here.
- **`chooseWeapon`'s range thresholds (`CLOSE_RANGE`, `MORTAR_MIN_RANGE`) and `aimAndFire`'s tolerance/jitter are all "ours" picks with no T2 script backing**, unlike almost every number elsewhere in this codebase, which cites a real script constant. T2's own weapon choice was a human's own judgment call, not a datablock field, so there is no script number to cite here — this is stated plainly rather than dressed up as sourced.
- **Bot difficulty is explicitly out of scope** (per the given scope), so `AIM_JITTER_DEG`/`AIM_TOLERANCE_DEG` are fixed constants, not a per-bot or per-team difficulty knob. A future milestone wanting difficulty tiers would scale these two numbers (and perhaps `VISION_RANGE`) per bot rather than inventing new mechanics.
- **A bot never fights from inside a vehicle, and never targets an enemy vehicle or its driver with ground weapons — deliberately out of scope, not an oversight.** A mounted enemy is excluded from `findNearestVisibleEnemy` entirely (Task 4, failure-matrix row 18) because M5's own damage model makes a mounted player's hitbox un-hittable; without a Shrike-blaster-equivalent bot weapon or vehicle-vs-vehicle targeting logic (neither in the given scope), the only correct behavior this milestone is to not engage. A follow-up milestone adding bot vehicle combat would need `findNearestVisibleEnemy` (or a sibling function) to consider `world.vehicles` as its own target class, not just extend the existing player scan.
- **Issues `strml/clans#25` (decoded vehicle `kind` unvalidated) and `#26` (destroyed vehicle slots freed but never deactivated) do not reach this milestone's bot logic.** Both are decode-path bugs against the *client's* snapshot-decoded `vehicles` array (`packages/client`). Bots run entirely server-side against the authoritative `World.vehicles`, never a decoded snapshot: `kind` there is always a value `spawnVehicleAtPad` itself wrote (already validated at that call site per M5 review round 1's finding 1), and `findMountableVehicle`/`shouldUseVehicle` (Task 7) both check `active`/`destroyed`/`driverId` directly on the real store, so a destroyed vehicle is never offered as a goal regardless of #26's client-side symptom. No bot-side workaround is needed for either; noted here so a future reader doesn't assume these issues block M6.
